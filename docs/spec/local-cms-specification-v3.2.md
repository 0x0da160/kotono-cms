## 1. 目的と基本方針

- 単一のHTMLファイルをデスクトップブラウザで `file://` 起動する。iOS・iPadOSでは同じHTMLをhttpsの固定オリジンから配信する（第38.5節）。
- Webメディアの記事の作成・編集に特化する。
- 記事データはMarkdown＋YAML frontmatterで保存する。
- デスクトップではユーザーが選択したローカル作業ディレクトリを、iOS・iPadOSではブラウザ内の作業場所（第38章）をストレージとする。Git管理の有無にかかわらず編集できる。
- サイト表示用フロントアプリケーションは別途用意する。
- CMS自身は記事配信用Web API、サイトのビルド、配信、予約実行を提供しない。
- コンテンツ編集とサイト表示を分離したヘッドレスCMSとする。
- 保存済みデータを無断で整形・移動・削除しない。検出した外部変更を無確認で上書きしない。
- 異常時のデータ状態、編集内容の退避、再試行可能性を通常時の機能と同等に扱う。

### 1.1 操作の意味

| 操作 | 意味 |
| --- | --- |
| 保存 | 編集内容をローカルファイルへ書き込む |
| 変更を記録 | 保存済みの対象記事の変更をGitへコミットする |
| 同期 | GitHubとの変更の送受信。CMSはREST APIによるpush・pullと簡易マージを提供する（第40章）。外部Gitクライアントでも行える |
| 公開 | フロント側のデータ解釈・ビルド・配信。CMSの保存・コミットとは別 |
| 再読み込み | 指定した範囲のディスク状態を読み直す。未保存内容を黙って破棄しない |
| 編集の破棄 | メモリ上の未保存編集を捨てる。保存済みファイルや取り込み済み画像は削除しない |

### 1.2 不変条件

1. 正常記事のフォルダ名とfrontmatterの `id` は一致する。
2. 通常編集ではID・保存先を変えない。
3. 同一CMSインスタンス内のディスク変更操作は直列化する。
4. 記事外のファイル、別記事、既存の無関係なGitステージを黙って変更しない。
5. 読み込み不能・不正な記事があっても、一覧全体と無関係な正常記事の編集を止めない。
6. 操作失敗・部分成功・結果不明を成功として表示しない。
7. 技術検証で満たせない要件を、無断で仕様から外したり別方式へ置換したりしない。

### 1.3 要件の優先度と未成立時の扱い

- P0：方式と保証境界の成立が必要。未合格の機能を出荷しない。GitがMVPから自動的に外れることを意味しない。
- P1：MVPの受け入れ条件。安全性・性能・復旧・アクセシビリティを含む。
- P2：改善推奨。ただし本版で「必須」とした項目はMVP条件となる。
- 「安全に確認」「安全に停止」「照合」は、観測API、基準データ、停止時点、残存状態、回復操作まで定義して初めて実装済みと扱う。
- 取得できない属性を捏造して互換性を装わない。操作結果を推測だけで成功としない。

## 2. 対応環境と技術成立性ゲート

### 2.1 対応環境

| 項目 | 仕様 |
| --- | --- |
| ブラウザ（デスクトップ） | リリース時のデスクトップ版Chrome・Edge安定版のうち、環境表で検証済みの版 |
| OS（デスクトップ） | Windows・macOS。具体的な版は検証記録とリリースノートで固定 |
| ブラウザ（モバイル） | iOS・iPadOS 26以降のSafari、およびホーム画面に追加したWebアプリ。環境表で検証済みの版 |
| 端末（モバイル） | iPhone・iPad |
| Firefox・macOS版Safari・Android・その他OS | 動作保証対象外 |
| 起動 | デスクトップは単一HTMLの `file://` 起動。iOS・iPadOSは固定オリジンからのhttps配信（第38.5節） |
| ローカルサーバー | 利用者による起動は不要。iOS・iPadOS向けには静的ファイルの配信元が1つ必要 |
| 配布物 | JS・CSS・フォント・依存ライブラリを含め、外部CDNに依存しない |
| フォルダアクセス | デスクトップはユーザーによる明示的な選択・権限付与を必要とする。iOS・iPadOSは実フォルダを扱わず、ブラウザ内の作業場所と取り込み・書き出しを用いる（第38章） |
| 次回起動 | フォルダ選択・権限の永続化を必須としない |
| 通信 | 配布物の取得と、ユーザーが操作した同期（第40章）での `api.github.com` への通信に限る |

起動時に必要なAPIと権限を確認する。実フォルダ用とブラウザ内の作業場所用の検査を分け、いずれかが成立する場合に起動する。非対応環境では理由を表示して編集を開始しない。必要なフォルダを選べない・必要な読み書きができない場合は、フォルダ再選択・権限付与を案内する。

## 3. リポジトリと記事フォルダ

```text
repository/
├── .git/                         # Git機能使用時
├── .gitattributes                # 存在する場合。CMSは自動変更しない
├── cms.config.json               # 省略可
└── content/
    └── articles/
        ├── k7m2x9q/
        │   ├── index.md
        │   └── media/
        │       ├── q7m2k9w4ac.jpg
        │       └── n6p3x8r5tz.webp
        └── p4c8n6w/
            └── index.md
```

- 1記事を1フォルダとする。本文ファイル名は `index.md` 固定。
- 記事フォルダは `content/articles/` の直下のみを対象とする。
- 記事IDがフォルダ名となる。タイトル・slug・日時の変更でフォルダ名を変えない。
- 記事固有メディアは `media/` に置く。メディアがなければ省略可。
- CMSが生成する画像参照は `./media/ファイル名` とする。
- 未知のファイル・サブフォルダは通常保存では保持する。
- 隠しファイルを含め、フォルダ内の全ファイルが記事削除の対象となる。削除時は一覧で確認させる。
- 記事領域やメディア領域から外へ出るパス、シンボリックリンク等の間接参照を辿って読み書きしない。文字列パス検証と実エントリー検証を分離する。観測API・停止条件・OS別試験は第31・32章に従う。観測能力が足りず通常操作の成立を証明できない場合も、技術ゲート未合格とする。
- `index.md` がないフォルダは不完全な記事として表示し、自動生成・自動削除しない。
- 期待するディレクトリ位置に同名の通常ファイルがある場合はエラーとし、置換しない。

### 3.1 初回フォルダ準備

`content/articles/` がない場合は作成予定パスを示し、確認後に作成する。閲覧のために無断作成しない。`cms.config.json` がない場合は既定値で動作する。Gitの初期化は独立した明示操作とする。

## 4. 設定ファイルとバージョン

### 4.1 設定例・既定値

```json
{
  "schemaVersion": 1,
  "articleId": {
    "length": 7
  },
  "media": {
    "maxFileSizeMiB": 20,
    "maxPixelCount": 40000000,
    "maxBatchFiles": 50
  }
}
```

| 項目 | 許容範囲 | 省略時 |
| --- | --- | --- |
| `schemaVersion` | 整数 `1` | 初期版設定との互換のため `1` |
| `articleId.length` | 整数7〜32 | 7 |
| `media.maxFileSizeMiB` | 整数1〜100 | 20 |
| `media.maxPixelCount` | 整数1〜100,000,000 | 40,000,000 |
| `media.maxBatchFiles` | 整数1〜100 | 50 |

容量は1 MiB＝1,048,576バイトとして判定する。上限変更は将来の取り込みにのみ適用し、既存ファイルを自動削除しない。これらは安全・性能上の制限であり、上限内の全データで性能を保証するものではない。

### 4.2 不正設定と影響範囲

- 設定ファイルがない：既定値で動作する。
- JSON構文エラー・ルート型不正・未知の `schemaVersion`：閲覧・既存記事の編集は可能。新規作成・複製・メディア取り込み・設定書き込みを停止し、外部エディタでの修正を案内する。
- ID長のみ不正：新規作成・複製だけを停止する。
- メディア設定のみ不正：メディア取り込みだけを停止する。
- 未知の設定キー：値を無視して警告し、ファイルから削除しない。
- 設定の外部変更：再読み込みで反映する。新規作成・複製・取り込みの開始前にも最新設定を確認する。

初期版に汎用設定エディタは設けない。明示的な「既定設定を作成」操作は、設定が存在しない場合に限る。既存設定を上書きしない。設定の変更・削除・Gitコミットは外部ツールで行う。

設定ファイルは第34.5節の読込前バイト上限と解析中の構造・時間上限を適用する。上限超過・予算内での検証不能は構文不正等と同様に閲覧・既存記事編集を維持し、新規作成・複製・取り込み・設定書き込みを停止する。全文読込後のサイズ判定だけで上限を実装しない。

### 4.3 設定値と固定安全上限

- 第4.1節の値は取り込みのユーザー設定上限であり、既存ファイルの無条件表示許可ではない。
- アプリ固定の資源予算は第34章に定義する。設定ファイルから緩和できない。
- 実効上限は、設定上限と固定安全上限の小さい方とする。画面で両者を確認できる。
- 予算を超える既存ファイルは保持し、読み取り・デコード・描画の該当処理だけ停止する。
- 初期版に汎用設定エディタは設けないが、復旧ドラフトの有効化・停止・一覧・削除・退避は専用のプライバシー設定として提供する。リポジトリ設定ファイルには書き込まない。

## 5. 記事ID

### 5.1 形式と生成

- Nano IDの安全な乱数生成を使用する。
- 使用文字は次の小文字Base32の32文字とする。

```text
0123456789abcdefghjkmnpqrstvwxyz
```

- 新規ID長は設定値。既定7文字、設定可能範囲7〜32文字。
- 既存記事も7〜32文字かつ上記文字種であれば、現在の設定と異なる長さを許容する。
- 日時・タイトル・slug・端末識別子を含めず、ソート可能性を要求しない。
- 作成後は不変。同一記事の別ブランチでの編集では維持する。
- 通常編集での変更は禁止。衝突解消とID不一致修正は明示的な例外とする。

### 5.2 重複検査

1. 設定された長さで生成する。
2. 作成先の同名エントリーの有無を確認する。記事として正常かどうかは問わない。
3. 存在すれば再生成する。初回を含め最大11候補。
4. 上限到達時は停止し、設定変更・ディレクトリ確認を案内する。
5. 既存エントリーを再利用・上書きしない。

検査と作成の間の外部操作に対する完全排他は保証しない。作成時に既存エントリーが見つかった場合や所有を確認できない場合は停止し、既存データへ書き込まない。

### 5.3 新規エントリーの所有確認

- 存在確認後に`create: true`でハンドルを得たという事実だけでは、自分だけが新規作成した証拠としない。
- 記事フォルダ、index.md、画像、設定、退避先、Gitロックについて、存在確認・取得・初回書き込みの間に外部作成を注入する。
- アダプター設計に、利用API、所有確認根拠、競合窓、停止可能時点を記録する。
- 完全な排他的作成を実証できない場合、外部書き込み禁止運用下での保証と、外部競合時の非保証を操作前の条件として明示する。通常運用下で既存データを上書きしないことの実証は必要。
- ランダムIDは偶発衝突低減策であり排他・所有確認の代替ではない。不明な既存内容や種類の違いを検出した場合は書き込みを止める。
- API上の限界が不変条件と両立しない場合は再合意する。「所有確認済み」という虚偽の内部状態で回避しない。

## 6. frontmatterの標準スキーマ

```yaml
---
id: "k7m2x9q"
title: "記事タイトル"
slug: "article-slug"
status: "draft"
createdAt: "2026-11-03T22:08:00+09:00"
updatedAt: "2026-11-03T22:08:00+09:00"
publishedAt: null
tags: []
cover: null
---
```

| 項目 | 型・制約 |
| --- | --- |
| `id` | 文字列。記事フォルダ名と一致。通常変更不可 |
| `title` | 文字列。下書きは空文字可。公開状態は空白だけでない値が必須 |
| `slug` | 文字列。第7章に従う |
| `status` | `draft` または `published` |
| `createdAt` | 第8章の日時文字列。通常変更不可 |
| `updatedAt` | 第8章の日時文字列。保存時にCMSが管理 |
| `publishedAt` | 第8章の日時文字列または `null`。公開状態は日時必須 |
| `tags` | 文字列配列。空配列可。空・空白のみの要素と完全一致の重複は禁止 |
| `cover` | `null` または `src`・`alt` を持つマッピング |

```yaml
cover:
  src: "./media/q7m2k9w4ac.jpg"
  alt: "画像の説明"
```

- `cover.src`・`cover.alt` は文字列。altの空文字は許容する。
- coverは当該記事の `media/` 内のローカル画像を指す。外部URLや記事領域外の値は保存時の検証エラー。
- 未知のトップレベルフィールドと、cover内の未知フィールドを保持する。
- タグは大文字小文字を区別して保持し、自動統合・自動トリムしない。フォーム入力時は確定前に空白を可視化して検証する。
- 下書きでも標準項目の存在と型は必須。未知フィールドだけを理由に保存を止めない。
- createdAtは原文モードでも通常変更不可。既存記事の不足・型不正を修正する場合に限り、専用の確認付きメタデータ修正操作で変更できる。正常な値の任意変更は外部ツールで行う。

## 7. slugと公開状態

### 7.1 slug

- 正規表現 `^[a-z0-9]+(?:-[a-z0-9]+)*$` に適合する。
- 最大128文字。下書きの空文字は例外として許容する。
- 先頭・末尾・連続ハイフンは禁止。手動入力し、自動生成しない。
- `content/articles/` 内の全記事を対象に、下書きも含め完全一致の重複を検査する。空文字同士は重複ではない。
- 公開状態は非空必須。下書きでも入力済みなら形式と重複を検証する。
- 公開後の変更は可能だが、URL変更の警告と確認を行う。
- リダイレクト生成・ルートの予約語との衝突検査はフロント側の責務。CMSは汎用の予約語を内蔵しない。
- slug変更・新規記事保存・公開状態への変更時は、一覧キャッシュだけに頼らず記事領域を再走査する。列挙、frontmatterの有界取得、slug抽出、完全検証を分離し、本文の無条件全文読込を避ける。
- 記事の追加・削除・slug変更を検出した場合は索引を更新する。
- 読み取り不能等により一意性を確認できない場合、該当操作を停止して「重複検査不能」と表示する。単なる重複なしとは表示しない。
- 不正記事でもslugを安全に取得できる場合は重複検査に含める。関係のない記事の重複だけでは当該記事の保存を止めない。
- 保存済み既存記事でslug・公開対象条件を変えない通常の本文・タイトル修正は、他記事が読めないという理由だけで全体重複検査を必須にしない。当該記事の既知の不正slug・既知の重複は修正が必要。
- 再走査は複数ファイルの同時点スナップショットを保証しない。外部書き込み禁止運用を前提とし、走査後の競合を含む一意性の非保証を保証境界表に記載する。
- 未検査・検査不能件数を表示する。抽出不能を「空slug」と見なさない。

### 7.2 状態遷移

| 操作 | 結果 |
| --- | --- |
| 新規作成 | `draft`、`publishedAt: null` |
| 初めてpublishedへ変更 | publishedAtがnullなら変更時刻を入力。保存前に変更可能 |
| 公開状態の記事を編集 | publishedAtを維持 |
| draftへ戻す | publishedAtを保持 |
| 再びpublishedへ変更 | 既存publishedAtを維持 |
| 公開日時を編集 | 有効な過去・未来日時を許容 |
| publishedで保存 | title・slug・publishedAtの条件を満たすこと |

フロントの公開対象は `status == published` かつ `publishedAt <= 現在時刻` とする。比較は文字列順ではなく同一の時間軸に変換して行う。

未来日時は「公開予定日時」と表示する。「配信予約完了」と表示しない。CMSは公開・非公開の配信反映、指定時刻のビルド、デプロイ完了を確認しない。静的サイト等では別途ビルド・配信の仕組みが必要となる。

### 7.3 UIの状態軸

- 原稿状態：下書き／公開対象。`published`の日本語表示は「公開対象」とする。
- 公開日時：未設定／過去または現在／未来。未来は「公開予定日時を設定済み」とする。
- 保存：未保存／保存中／保存済み／結果不明。
- Git：未記録／記録済み／状態不明。未保存と別に表示する。
- 配信：本CMSでは未確認。「公開済み」「配信予約完了」「デプロイ成功」を推定表示しない。
- 公開日時の入力箇所に、日時設定だけではビルド・配信されないことを表示する。

## 8. 日時・更新判定・改行

### 8.1 日時の形式

- 許容形式はオフセット必須のRFC 3339形式のサブセットとする。
- 年は4桁、秒は必須、小数秒は省略または1〜3桁、タイムゾーンは `Z` または `±HH:MM` とする。
- 年は0001〜9999。月日・時分秒を厳密に検証し、24時表記、うるう秒、存在しない日付、オフセットなしの日時、形式にない表現は拒否する。
- `T`・`Z`は大文字のみ。オフセットは00:00〜14:00の絶対値、14時の場合は分00のみ。未知オフセットを意味する`-00:00`は拒否し、`Z`・`+00:00`は許容する。
- 文字列全体が文法に一致することを検証し、前後空白・自動日付繰り上がり・曖昧なDateパースを許容しない。
- 境界例：2000-02-29は有効、1900-02-29は無効。+14:00は有効、+14:01・+15:00・-00:00は無効。小数秒4桁は無効。
- CMS生成値は秒精度で端末のローカルオフセットを付ける。
- 既存値・手動入力値は有効ならオフセット表記を保持する。
- 表示は原則端末のローカル時刻。詳細で保存値とタイムゾーンを確認できる。
- 時計は端末時計に依存し、正確性・単調増加は保証しない。

### 8.2 変更判定

以下を別々に管理する。

1. 未保存判定：現在の編集内容が最後の保存基準と異なるか。独自項目、コメント、書式変更も含む。
2. 書き込み判定：検証と必要な正規化後の保存候補がディスク内容と異なるか。
3. updatedAt更新判定：本文、id以外の標準値、未知フィールドの値・構造のいずれかが変わるか。

- コメント・引用符・キー順等の表現だけの変更は保存するが、updatedAtは変更しない。
- 改行コードだけの変更はupdatedAtを変更しない。
- 本文の空白・末尾改行の変更は本文変更としてupdatedAtを更新する。
- `updatedAt` だけの原文編集は拒否し、CMS管理項目であることを表示する。
- 変更後に完全に元へ戻した場合は未保存扱いを解除する。
- 未変更のまま保存しても書き込まず、CRLFの正規化も行わない。
- 実際の保存が発生する場合は記事ファイル全体をLFに統一する。frontmatterだけの編集でも同様。
- 新規記事のcreatedAtは編集開始時刻として文書へ保持し、初回保存の再試行や復旧ドラフトからの再開でも取り直さない。updatedAtは初回保存の最終候補生成時刻。複製は最終index候補確定工程で取得した同一の時刻を両方に設定する。保存候補の管理値は成功確認後に保存済みとして採用し、工程終了時刻との厳密一致は意味しない。
- updatedAtは各保存試行の候補生成時に一度だけ取得し、候補と一緒に保持する。再読込でその候補が保存済みと確認できた場合は、その候補時刻を採用する。
- 保存失敗時にupdatedAtの更新を成功済みとして扱わない。再試行で新たな書き込み候補が必要な場合だけ時刻を取り直す。UI復旧だけの再試行で時刻を書き換えない。

### 8.3 意味的同値の規則

- 文書ノードの型を保持して比較し、JSON化・JavaScript Numberへの丸めを行わない。
- 文字列はデコード後の文字列の完全一致。数値と文字列、nullと空文字、配列とマッピングは異なる。
- 配列は要素順を含めて比較する。マッピングはキーと値を比較し、キー順だけの変更は表現変更とする。重複キーは比較前にエラー。
- 整数は精度を失わない整数値で比較する。浮動小数は採用パーサーの表現を無検証でNumber化しない。十進数・指数表記は精度を保持する比較規則を実装し、未対応なら当該文書の保存を止める。
- YAML core schemaの特殊数値は種類を保持し、NaN同士は同値、正負の無限大は区別する。正負のゼロは意味的に同値とする。元のノード表現は維持する。
- 真偽値・nullは型付きの値で比較する。アンカー等の非対応構文は比較の前に拒否する。
- 日時は文字列型だが、標準日時フィールドのupdatedAt判定では時間軸上の同値を用いる。オフセット表記だけの変更は保存するがupdatedAtを更新しない。
- 本文比較は改行コードをLFに揃えた上で行う。空白・末尾改行の変更は本文変更。BOM除去は意味変更としない。
- 巨大整数、指数、-0、NaN、マッピング順、引用符、日時オフセットについて同値／非同値の受け入れフィクスチャを持つ。

## 9. YAMLと原文の保持

### 9.1 文書形式

- ファイルはUTF-8。読み込みではUTF-8 BOMを許容し、実際に保存する場合はBOMなしUTF-8にする。
- 先頭の独立した行`---`で開始し、その後の最初の独立した行`---`で終了する。独立行は行内容がASCIIの`---`ちょうどであるものとし、行終端はLFまたはCRLF。区切りの前後空白は許容しない。開始前はBOM以外を置かない。
- 区切り探索はYAML解析より先に行う。インデントされたブロックスカラー内の`  ---`は区切りではない。引用符内を含め、非インデントの独立行`---`は常に終端とする。そのような生行を必要とするYAML表現は本形式の対象外。
- 開始区切り後から閉じ区切り前までをfrontmatter容量としてUTF-8バイト数で数える。上限内に閉じ区切りがない場合、全文を探索せずエラーとする。
- 閉じ区切りとして `...` は採用しない。
- 閉じ区切りより後はすべてMarkdown本文とし、本文中の `---` は再解析しない。
- 本文の末尾改行は保持し、自動追加・自動削除しない。新規記事は標準テンプレートで生成する。
- 不正なUTF-8は黙って代替文字に置換して保存しない。読み取り専用とし、元ファイルの退避・外部修正を案内する。

### 9.2 YAMLの対応範囲

- YAML 1.2のcore schemaを基準とし、ルートは文字列キーのマッピング1文書のみ。
- 標準フィールドは第6章の型で検証する。日時を暗黙にDateオブジェクトへ変換しない。
- 未知フィールドはYAMLの文書ノード上で保持し、全体をJSON互換オブジェクトへ変換して再生成しない。
- マッピングのキー重複はエラー。
- 未知フィールドの通常のスカラー・配列・マッピングを保持する。
- アンカー・エイリアス・マージキー・独自タグ・非文字列キーを含む文書は初期版ではフォーム編集・保存対象外とする。安全な範囲で閲覧・原文コピーを許可し、外部ツールでの修正を案内する。自動展開・タグ削除はしない。
- 未知フィールドの大きな整数等はノードを保持し、JavaScriptの数値精度で丸めない。
- frontmatter上限は1 MiB、入れ子上限は50段。上限超過は読み取り専用として原因を表示する。
- エイリアス展開は不要な処理で行わず、パーサーの資源制限を有効にする。制限値と上記判定を回避できないことを試験する。

### 9.3 保存時の保持契約

| 対象 | 保持方針 |
| --- | --- |
| 未知フィールド | 値・構造を保持し削除しない |
| YAMLコメント | 保持する |
| 既存キー順 | 維持する |
| 未変更ノードの書式 | 採用パーサーのノード・トークン保持機能を使い、受け入れフィクスチャで保持を確認 |
| 変更した項目の書式 | 必要なノードだけ変更。無関係なノードを再整形しない |
| Markdown本文 | frontmatterのみの変更では、LF統一とBOM除去以外は保持 |

新規記事は標準項目の掲載順で生成する。全体の自動整形は禁止。完全なバイト一致は保証しないが、値・構造・コメント・キー順の欠落を許容しない。保持できない構文を黙って保存せず、保存を停止する。

### 9.4 コメントの帰属と保持

- コメントは保持するだけでなく、無関係な項目へ誤って移さない。
- 未変更ノードに帰属する前置・行末コメントは、そのノードとの関係を維持する。
- 値のみ変更する場合は、キーに帰属するコメントを維持する。
- コメント付きキーを原文で削除する場合、ユーザーが削除したコメントも削除可能。フォームの操作だけで未知フィールドやそのコメントを削除しない。
- スカラー型変更等で元位置を維持できないコメントは差分で明示する。欠落・曖昧な再配置を黙って確定せず、保持不能なら保存停止。
- 許可する再配置と保持不能の例を保持フィクスチャに記載する。コメントの文字列だけが残ることを合格条件にしない。

## 10. 新規作成・複製・記事ID修正

### 10.1 新規作成

- 作成開始時にID候補とcreatedAtを設定する。初回保存前はメモリ上の未保存記事とする。
- 初回保存直前に最新設定とID重複を再確認する。候補が既に存在する場合は再生成し、表示を更新する。
- 初回保存成功までは画像取り込みを行わない。先に下書き保存を案内する。
- 初回保存前のキャンセルでは記事フォルダを残さない。
- 正常なindex.mdは、作成予定ファイルの書き込みと検証が完了した最後に確定する。空・欠落・不正なindex.mdを含む残存先は不完全／要確認とし、成功扱いしない。
- 新規記事の取消・画面移動にも未保存確認を適用する。

### 10.2 複製

- 保存済みの正常記事のみを複製可能とする。未保存なら保存または破棄を先に選ばせる。
- 複製元の最新状態を再確認し、読み込み後に変わっていたら停止して再読み込みを案内する。
- 新しいIDを生成し、title・本文・タグ・cover・未知フィールドを保持する。
- statusはdraft、slugは空文字、publishedAtはnullにする。
- createdAt・updatedAtは、最後の正常index.md候補を確定する工程の時刻にする。成功確認後に採用する。
- 記事フォルダ内の通常ファイル・サブフォルダを、未知ファイルも含めてコピーする。コピー予定一覧・総容量を実行前に表示する。
- シンボリックリンク等、安全に複製できないエントリーを含む場合は操作を止める。
- media内のファイル名を維持し、記事内相対参照を維持する。
- 未知フィールド内のID・外部参照・固有値は自動変換しない。複製前に注意を表示する。
- index.md以外のコピーと検証を先に完了し、正常なindex.mdを最後の完成マーカーとして確定する。コピー元のindex.mdを先に完成形で置かない。
- 列挙時の集合、コピー対象の内容、最後の元データ再照合を行う。検出した外部変更は停止する。同時点スナップショットは保証しない。
- 途中失敗時は完成記事として表示しない。残存先を明示し、再試行で無確認に上書きしない。
- index.md確定後に再起動した場合、実ファイルの整合性から完成を判断する。原因を断定できない状態は「要確認」とする。完成マーカーは原子的一括コピーや耐電断性の保証ではない。
- 再帰列挙・コピー予定の上限は第34章に従う。

### 10.3 ID不一致と合流時の衝突

- フォルダ名とfrontmatterのidが違う場合は通常保存を停止する。
- フォルダ名が有効なら、フォルダ名を正としてidのみを直す専用操作を、差分表示・確認付きで提供する。
- 合流で同じパスに独立した記事が追加された疑いがある場合、同一記事の編集競合と区別して案内する。
- 初期版に専用のGit衝突解決UIは設けない。外部ツールで一方に新IDを割り当て、フォルダ名とidを一致させ、画像もフォルダ単位で保持する。
- 一方を無確認で削除・上書きしない。解決後はslug・参照・ID一致を再検証する。
- 全件frontmatter検査だけで、合流時のID衝突を確実に検出できるとはみなさない。

## 11. 操作状態と遷移

### 11.1 主な状態

| 状態 | 意味・許可操作 |
| --- | --- |
| 未選択 | フォルダ未選択。編集不可 |
| 読み込み中 | 初期走査または再読み込み。途中件数・エラーを表示 |
| 保存済み | 現在の編集内容と保存基準が一致 |
| 編集中 | 未保存内容あり |
| 検証エラー | 編集・コピー可。通過するまで保存不可 |
| 保存中／操作中 | 対象を固定し、変更操作を直列実行 |
| 外部変更あり | 保存を停止。3版の識別・退避・再読み込みを案内 |
| 権限不足 | 編集内容を維持。再認可・退避を案内 |
| 操作失敗／部分成功 | 成否と残存状態を表示。状況を確認して再試行 |
| 結果不明 | 再走査・照合まで追加の破壊的操作を停止 |
| 読み取り専用 | 非対応形式・不正ID等。許可される閲覧・コピーのみ |

未保存状態、Git未コミット状態、権限、検証、処理状態は別の軸で管理する。例えば、保存済みかつ未コミット、編集内容は正常だが権限不足、といった組み合わせを表示できるようにする。

### 11.2 操作中の制御

- 保存・作成・複製・削除・画像取り込み・画像削除・Git書き込み・設定作成は同一キューで直列化する。
- 本版では保存スナップショットと編集リビジョンを分離する。スナップショット確定後は次リビジョンの本文・フォーム編集を許可する。原文／フォーム切替も単一文書の整合性を保つ範囲で許可する。
- 保存成功で基準版を更新するのは保存したリビジョンまでとする。後続編集があれば未保存のまま残す。保存した古い本文を現在の編集へ戻さない。
- 通常の保存等で入力を止めるのはスナップショット固定等の短い確定工程のみ。目標100 ms以内とし、超過時は原因と改善を記録する。破壊的操作の対象記事に限る編集制御は第11.3節を適用し、通常保存の入力停止とは分けて測定・表示する。
- ディスクキューの直列化を理由にUI全体を停止しない。Git・画像取り込み中も安全な本文編集・コピーを可能にする。画像削除・記事削除等が未保存禁止である条件は維持する。
- 操作中のフォルダ切り替えと破壊的操作は無効化する。黙って後続キューに積まない。
- キャンセル可能な処理では安全な境界でキャンセルする。既に完了したファイル操作を取り消したとは表示しない。
- 長時間処理はキュー待ち／検証／実行／確定／結果照合の工程、進捗、取消可否を表示する。取り消せない短い確定工程はその旨を表示する。取消操作の受理と実際の停止を区別する。

### 11.3 削除中の対象編集と確定点

- 削除の対象記事・対象ファイル集合・確認時の編集リビジョンを固定する。未保存禁止は開始時だけの検査ではなく、削除確定まで維持する。
- 記事削除では、最初の削除確認画面を開く時点から、取消・停止・失敗・完了まで対象記事の編集を禁止する。本文・フォーム・原文・Undo/Redo・画像挿入等、内容を変える全経路を含む。コピー・原文退避・状態確認は可能とする。
- 画像削除では、確認・退避中の本文編集は許可する。ただし確認時から編集リビジョンが変わった時点で、その確認を失効させ、未実行の削除を停止する。内容が元へ戻っていても旧確認を流用せず、保存または破棄後に再確認する。退避済みファイルは保持する。
- 画像の個別削除は、対象記事の編集を一時停止し、未保存なし・確認リビジョン一致・最新の保存済み参照・対象内容・退避検証済みを再照合してから削除APIを呼ぶ。APIの結果照合まで対象編集を再開しない。最終照合と削除API呼出しの間に新たな編集を受け付ける競合窓を作らない。
- 画像の削除APIと結果照合は取消不能となる範囲と待ち状態を表示し、対象編集の停止時間を測定する。I/O待ちを通常100 ms以内のスナップショット確定工程と同一視しない。安全性を保つ停止境界が実現できなければ技術ゲートで方式を再検討する。
- 複数画像の個別削除間で編集を再開する場合も、リビジョン変化で残りを停止する。既に削除した対象は自動復元せず、削除済み・残存・不明を表示する。
- 制御範囲は対象記事に限定し、別記事の安全な編集やUI全体をロックする理由としない。別記事への移動等は第11.2節・第13.1節の既存条件に従い、操作対象を差し替えない。
- 記事削除により存在しなくなった文書を、同じ保存先へ通常保存できる編集中記事として残さない。コピー・退避と削除結果の確認を提供する。


## 12. 同時編集・外部変更・排他の保証

- 同じ作業フォルダを編集するCMSは同時に1つとする。
- 別タブの同一フォルダ利用を検出した場合、後から開いた側の書き込みを止める。
- タブ間検出はベストエフォート。`file://` のオリジン・通信制約を含め実機検証する。
- iOS・iPadOSの作業場所は外部アプリから変更されない。別タブ・取り込み・pullによる変更を本章の外部変更として扱う。
- 複数タブ・複数アプリ・外部Gitクライアントを含む完全な排他は保証しない。
- 外部エディタ・GitクライアントはCMSの保存・ディスク変更操作と同時に実行しない運用とする。
- 対応環境では `createWritable()` のexclusiveモードを使用する方針を検証する。ただし外部プロセスも含む完全排他とは説明しない。

### 12.1 保存前比較

読み込み時のファイル全体の内容を基準版として保持し、保存直前にディスク版とバイト単位で比較する。内容ハッシュを用いる場合は暗号学的ハッシュとファイルの存在確認を用い、サイズ・mtimeだけで同一とみなさない。

次の場合は保存を止める。

- 内容が変わった。
- ファイルが削除された、別種のエントリーになった。
- 権限や読み取りエラーにより比較できない。

比較後から書き込みまでの競合を完全には防げない。保証は「検出した外部変更を無確認で上書きしない」であり、「外部プロセスとの競合で絶対に上書きしない」ではない。

### 12.2 外部変更時の支援

読み込み時の原文、現在のディスク原文、編集中の原文を区別する。各版の取得時点と内容識別子を表示し、標準メタデータの差分と上限付きの原文行差分を提供する。差分予算超過時は省略理由と各版の退避を提供し、「差分なし」としない。編集中の原文をコピーまたはユーザー操作によるダウンロードで退避可能にする。自動マージ・強制上書きは提供しない。再読み込み前には未保存編集の保存不能・退避・破棄を明示する。

削除・複製・画像削除・コミットも、確認時と実行時の対象を照合する。検出した変更が対象・内容・危険性を変える場合は停止し、新しい内容で再確認する。

## 13. 保存契約と失敗時の安全性

### 13.1 手動保存

- 保存ボタンまたはCtrl/Cmd＋Sでリポジトリへ保存する。リポジトリへの自動保存はしない。
- 別記事・別フォルダへの移動では、保存・破棄・キャンセルを選ばせる。破棄はディスクだけでなく、対応する復旧ドラフトの扱いを明示する。
- タブ・ウィンドウを閉じる際は離脱警告を試みるが、表示を保証しない。
- 未保存、最後のリポジトリ保存時刻、経過時間、復旧ドラフトの退避状態、原文退避操作を常時確認できるようにする。
- クラッシュ対策として、ブラウザ内の復旧ドラフトを提供する。これはリポジトリへの保存・Git記録・同期ではない。第33章に従う。
- 保存できない状態でも原文のコピー・ダウンロード退避を可能にする。リソース上限超過時は元ファイルを無制限に読み込まず、利用可能な編集中スナップショットを退避する。
- 明示的に破棄した編集を次回起動時に黙って復活させない。破棄したリビジョンのドラフトは削除または破棄済み記録を付ける。

### 13.2 単一ファイル保存の成功条件

1. 編集スナップショットとリビジョン番号を固定する。
2. 設定・記事スキーマ・必要な全体検証を行う。
3. ディスク基準版を比較する。
4. 保存候補を作り、必要ならupdatedAtを更新し、LF統一・BOM除去等を適用した最終UTF-8バイト列を確定する。
5. 第13.2.2節に従い、最終候補の再読込可能性と編集対象の資源制限を検証する。
6. 検証済みの同じ候補を書き込みストリームへ書き、クローズする。
7. ファイルを再読み込みし、保存候補との一致を確認する。
8. 一致した版を新しい基準版とする。後続編集には第13.2.1節の管理値反映だけを行い、現在の正本文書が基準と一致する場合だけ未保存表示を解除する。対応する復旧ドラフトを保存済みとして整理する。

クローズだけで耐電断性やストレージの物理永続化を保証したと説明しない。再読込不一致・失敗時は成功表示せず、結果不明として編集スナップショットを保持する。

### 13.2.1 保存中の後続編集との整合

- 保存済みスナップショットと現在の正本文書を別に保持し、成功時に古い全文を現在文書へ代入しない。
- updatedAt等のCMS管理値は保存成功時に文書の管理領域へ反映する。後続の本文・フォーム・未知フィールド・コメント編集を保持する。
- CMSが行う日時反映、LF・BOM等の保存表現処理を、ユーザーのUndo対象へ混入させない。原文表示は管理値と現在編集の整合を保つ。
- 失敗時は、成功したと未確認の管理値を確定扱いしない。後続編集を含む退避と、試行した保存候補の退避を区別できる。
- 後続編集が保存内容と意味・表現とも同じに戻った場合は、管理値・保存正規化を反映した基準と比較して未保存を解除する。リビジョン番号の違いだけで永久に未保存にしない。
- 管理値反映がユーザーの原文編集と競合する場合は、該当箇所を明示し検証停止する。未知フィールドや本文を自動マージしない。

### 13.2.2 最終保存候補の再読込可能性

- CMSが正常保存する最終候補は、同じ版・同じ検証規則のCMSで再読込した際に、対応文書形式・記事スキーマ・対話編集対象の資源制限を満たすことを必須とする。外部プロセスの変更や後の権限失効等まで保証する条件ではない。
- 検証対象はフォーム値や編集途中の文字数ではなく、管理値反映・YAML直列化・LF統一・BOM除去後の最終UTF-8バイト列とする。記事全体5 MiB、frontmatter 1 MiB、深度・ノード数・キー数・単一スカラー等、第9・34章の読込・編集条件を適用する。
- 新規作成、通常保存、複製の最終index.md、ID不一致修正・メタデータ修復等、CMSが記事ファイルを生成・変更する全経路へ適用する。検証後に候補を変更した場合は再検証する。
- プレビュー・Markdown AST・DOM・ハイライトだけの予算超過は、それだけで原文保存を禁止しない。文書形式・スキーマ・読込編集条件が成立すれば、プレビュー停止を明示して保存できる。参照判定不能時の画像削除禁止は維持する。
- 上限超過や検証不能なら書込前に停止し、項目・実測値・上限・対処を示す。既存ファイルを変えず、現在の編集・Undo・コピー・手動退避を保持する。入力を黙って切り詰めない。
- 入力・貼付け・フォーム変更が編集対象の上限を超える場合は、変更前の検査で拒否するか、予算内の回復用編集状態で戻す・短くする・退避を可能にする。ディスクからの上限超過記事の読取専用扱いと、編集中に発生した上限超過の回復を区別する。
- 最終候補の解析・検証自体にも第34章の予算を適用し、同じイベントループの終了後タイムアウトだけで安全と扱わない。書込後の再読込一致試験は省略しない。


### 13.3 失敗・再試行

- 書き込み失敗時はメモリ上の編集内容を保持し、未保存または結果不明のままとする。
- 再試行前に実ファイルを読み直す。基準版・保存候補・第三の内容のどれかを識別する。
- 候補どおり保存されていることが確認できれば、重複書き込みせず成功へ遷移できる。
- 第三の内容なら外部変更として停止する。
- 空き容量不足、権限失効、読み取り失敗等を区別できる範囲で表示する。
- 検証前に元ファイルを空にする、失敗後に自動削除する等の破壊的な回復処理は禁止する。

### 13.4 複数ファイル操作

初期版では記事フォルダ全体の原子的な一括変更を保証しない。ファイル単位の成功と操作全体の成功を区別する。

- 作成・複製：index.md以外の全対象を保存・検証し、最後に正常なindex.mdを確定・検証した時点で完成とする。それ以前は操作中・不完全として表示する。
- 画像一括取り込み：ファイルごとに成功確定する。他ファイルの失敗で成功分を自動削除しない。
- 記事削除：すべての対象が消えたことを確認して成功とする。途中失敗なら残存パスを表示する。
- コミット：HEAD・index・履歴の照合で結果を判定する。
- 再起動後は不完全記事、画像参照切れ、Git状態を走査する。前回のメモリ上の操作履歴がない場合は原因を断定せず「要確認」と表示する。

記事リポジトリ内に独自の隠しトランザクション領域を新設しない。以下は別扱いとする。

- ブラウザ内部の一時処理と、第33章の復旧ドラフト。
- 明示選択したリポジトリ外の削除前退避領域。
- 採用Git実装が必要とする標準的な`.lock`等。種類・作成位置・寿命・中断後の扱いを記録する。存在するロックを自動削除しない。

独自のリポジトリ内ステージング領域が必要なら、位置・除外・残骸識別・削除確認・再開方法を再合意してから導入する。

## 14. エディタ・原文モード

- frontmatterフォーム、Markdownソースエディタ、プレビューで構成する。
- リッチテキスト編集は提供しない。
- プレビューは未保存内容を反映する。公開サイトの見た目やURLを保証しない。
- フォームと原文モードは同一の編集中文書を編集し、切り替えだけで保存・破棄しない。
- 原文からフォームへの切り替えで構文・スキーマ検証を行う。失敗したら原文とエラー位置を維持する。
- 未知フィールドの専用フォームは作らず、原文で編集する。
- 原文モードでもID・createdAt・updatedAt等の制約は保存時に適用する。
- 構文エラー中は原文の編集・コピー可。保存とフォーム編集は停止する。
- フォーム・原文・本文は単一の正本文書とリビジョン番号を共有する。各モードが独立した古い本文を正本として持たない。
- フォーム変更と原文変更を文書レベルの共通Undo/Redo履歴へ記録する。IME変換・連続入力等を意味のある単位へまとめ、モード切替自体は内容変更にしない。
- フォーム変更→原文変更→フォーム復帰→Undoでは、最後の原文変更を戻し、フォームの先行変更は維持する。Redoも同一文書へ適用する。
- 保存によってUndoを消去しない。履歴予算超過時の古い履歴の切捨ては通知する。現在文書・保存基準・保存中スナップショットを切り捨てない。
- 原文構文エラー中に最後の正常プレビューを残す場合は「古い版」と表示し、現在の原文を描画したと誤認させない。
- UndoでID・createdAt等を不正に変更できても、保存時の制約は回避できない。
- メタデータフォームの値を本文変更と誤認して本文を再生成しない。

### 14.1 日本語入力・アクセシビリティ

- 日本語IMEのcomposition中に、Enterやショートカットで未確定文字列を失わせない。保存時は変換確定を待つか、明示的に確定を案内する。
- キーボードのみで記事選択、検索、フォーム／原文移動、保存、エラー確認、退避、確認ダイアログ操作を完了できる。
- ラベル、見出し、ランドマーク、フォーカス可視化を提供する。色だけで状態を伝えない。
- モーダルの初期フォーカス、閉じた後の復帰、危険操作の既定選択を定義する。削除を既定のEnter操作にしない。
- 保存結果・失敗・進捗を支援技術へ通知する。頻繁な入力ごとの過剰な読み上げを避ける。
- 200%ズームおよび1280×720相当の表示領域で主要操作を利用可能にする。3ペイン固定を強制せず、単一ペイン切替を提供する。
- WindowsのNVDAとmacOSのVoiceOverを用いて、主要操作フローをそれぞれ検証する。具体版は環境表に記録する。

## 15. Markdown対応範囲

基本構文に表・チェックリスト等を加えたGFM相当とする。曖昧な「完全互換」は称さず、以下を優先する。

| 構文 | 扱い |
| --- | --- |
| 見出し・段落・強調・取り消し線 | 対応 |
| 箇条書き・番号付きリスト・引用・水平線 | 対応 |
| リンク・画像・参照形式リンク | 対応。安全性規則を適用 |
| 表・チェックリスト | 対応。チェック操作は本文エディタで行う |
| インラインコード・コードブロック | 対応。実行しない |
| コード言語指定 | 対応。対象言語のみハイライト |
| 本文中の単一改行 | 通常段落では表示上の改行にしない |
| 明示的改行 | 行末半角スペース2つ、またはバックスラッシュ |
| 生HTML | 描画・実行せず、文字として表示 |
| 脚注・数式・独自ディレクティブ・MDX | 初期版プレビュー対象外。原文保持 |

ハイライト対象はHTML、CSS、JavaScript、TypeScript、JSON、YAML、Bash、Python。非対応の言語指定はプレーンなコード表示とし、外部から文法定義を取得しない。

未対応記述を保存時に削除・変換しない。採用ライブラリとバージョン、拡張設定を記録し、フロント側へ描画規則とテスト用記事を提供する。同じライブラリの使用は必須にしない。

## 16. 信頼境界・プレビュー・通信

### 16.1 信頼しない入力

記事、frontmatter、設定、ファイル名、Gitメッセージ、エラー内容、外部で変更されたファイルを信頼しない。画面表示に際してHTMLとして挿入しない。生HTML禁止だけを安全性対策の全体としない。

- スクリプト、イベントハンドラー、MDX等の実行を禁止する。
- Markdownレンダリング結果にも許可要素・許可属性・URL検証を適用する。
- シンタックスハイライト出力も安全に扱う。
- 記事にブラウザAPI、フォルダハンドル、Git操作を呼び出させない。
- 配布HTMLのCSP等の防御策は実機制約を検証して設定する。CSPだけに依存しない。

### 16.1.1 権限と処理の分離

| 層 | 保持できるもの | 禁止事項 |
| --- | --- | --- |
| 権限保持層 | 選択フォルダのハンドル、書き込みキュー、Git実行権限 | 記事由来HTMLの実行、任意パス・任意API呼び出しの受付 |
| 解析層 | 予算内の文字列・バイト列・構文木 | フォルダハンドルの直接保持、通信、無制限解析 |
| プレビュー層 | 検証済み表示データ、許可済み画像表示資源 | スクリプト、親DOM、ハンドル、Git、フォーム送信、任意遷移 |

- 解析は終了可能なWorker等の隔離処理で行い、タイムアウト・メモリ増幅の予算を持つ。Worker利用がfile起動で成立することもゲート対象。
- プレビューはスクリプト不可・独立オリジンとなるsandbox付きiframeを基本方式とする。`allow-scripts`・`allow-same-origin`を与えない。必要な画像・スタイルが表示できるか検証する。
- 許可要素・許可属性・URL検証は隔離と併用する。生HTML、CSS、イベント、フォーム、埋め込みフレーム等を記事から注入させない。
- 外部リンクは親側で再検証した明示操作で開く。プレビューに任意ナビゲーション権限を与えない。
- 無スクリプト・独立オリジンiframe内のクリックを親が直接取得できると仮定しない。初期方式はiframe内のリンクを識別番号付きの非遷移表示とし、親側のリンク一覧で行先・原文を確認して開く。別方式へ変更する場合も隔離と明示操作を維持して試験する。
- メッセージを使う場合は送信元ウィンドウとセッション別の識別子、型・長さ・許可操作を検証する。opaque originではorigin文字列だけを認証根拠にしない。
- 権限保持層はパス文字列をそのまま実行せず、選択済み記事・許可済みファイルの識別子から対象を解決し直す。
- 想定外の要素・属性が描画層へ混入しても、親DOM・フォルダ・Git権限へ到達できないことを試験する。
- CSPのアプリ用・Worker用・プレビュー用ポリシーを分離する。通信、スクリプト、画像、フレーム、ベースURL、フォームを必要最小限にする。meta配信で無効なディレクティブへ依存しない。
- 単一HTMLへの埋め込みコードを理由に、無制限なevalや記事由来コード実行を認めない。隔離方式が成立しない場合は技術ゲート未合格とする。

### 16.2 ローカルパス

- CMSがプレビュー用に読む画像は当該記事のmedia内のみ。
- 相対パスを正規化し、区切り文字・URLエンコード・ドット区間を検証する。
- `..` による領域逸脱、絶対パス、任意のfile URL、OS固有の絶対表現は拒否する。
- `./media/../index.md` 等、画像領域から外れる参照を解決しない。
- `blob:` URLはCMSが読み込んだ許可ファイルから内部生成したものだけを利用する。記事が指定する任意のblob URLは採用しない。
- オブジェクトURLは記事切替・画像更新・プレビュー破棄時に解放する。
- 参照の検証と実ファイル取得で別の正規化規則を使わない。

### 16.3 外部URLとネットワーク

- CMSはCDN、解析、更新確認、画像取得等の自動ネットワーク通信を行わない。例外は、ユーザーが操作した同期での `api.github.com` への通信（第40章）と、iOS・iPadOS版の配布物の取得（第38.5節）に限る。CSPの `connect-src` もこれに限る。
- 外部画像は既定でプレースホルダー表示とし、自動取得しない。初期版には外部画像の読み込み許可機能を設けない。外部画像の原文は保持する。
- 外部リンクはhttp・https・mailtoのみを明示操作で開ける。相対リンクとフラグメントは原文・行先を表示し、ローカルサイト遷移として解決しない。
- javascript、vbscript、data、file等のリンクを実行しない。未知のスキームも拒否する。
- 外部リンクを開く操作は外部通信を伴うことを示し、新規タブで開く。遷移先からCMS側へアクセスさせない設定を用いる。
- CMS配布物への依存埋め込みと、記事からの外部通信の禁止を別々に試験する。
- ローカルファイル・内容・パスをログ送信しない。診断情報をユーザーが退避する場合は内容を確認できるようにする。

## 17. メディア取り込み

| 項目 | 仕様 |
| --- | --- |
| 対象 | JPEG・PNG・GIF・WebP・AVIF |
| SVG | 取り込み・プレビュー対象外 |
| 動画・音声・PDF等 | 取り込みUI対象外。既存ファイルは保持 |
| 保存先 | 当該記事のmedia/ |
| 名前 | ランダムID＋内容形式に対応する小文字拡張子 |
| メディアID | Nano ID、安全な乱数、記事IDと同じ文字集合、固定10文字 |
| 同名検査 | 当該保存先の全エントリー。初回を含め最大11候補 |
| 加工 | リサイズ・圧縮・変換・メタデータ除去をしない |
| 容量・画素数・一括数 | 第4章の設定 |
| 処理並列度 | デコード・保存を1ファイルずつ行う |
| alt | 入力可。装飾画像用の空文字を許容 |
| cover | 取り込み済み画像から選択。本文挿入は不要 |

### 17.1 検証・成功確定

- 拡張子や申告MIMEだけでなく内容形式を調べる。拡張子・内容の不一致は拒否する。
- 容量を先に検査し、可能な範囲でヘッダーから画素数を検査してからデコードする。
- 画像として読み込みできることを確認する。形式不正と環境非対応を識別できる場合は区別する。
- アニメーションの全フレーム負荷を画素数制限だけで保証しない。巨大・異常画像で停止しないことを試験し、必要な追加制限を技術ゲートで確定する。
- 同名候補がなくても保存時に存在を再確認し、既存画像を上書きしない。
- ファイルの書き込み・クローズ・再読み込み検証後を取り込み成功とする。
- 成功した画像だけを本文へ挿入できる。本文へ挿入するalt・パスをMarkdown構文に合わせてエスケープする。
- 複数画像は各画像のaltを確認してから挿入する。coverのaltは本文画像とは別に編集できる。
- 元メタデータを保持することを取り込み画面とヘルプに表示する。

### 17.2 一括処理・キャンセル

ファイルごとに未処理・検証中・保存中・成功・失敗・キャンセルを表示する。キャンセルは次のファイル開始前など安全な境界で受け付ける。成功分は保持し、未挿入分も管理画面で確認できる。失敗時に残存ファイルがある場合はパスと状態を明示する。

画像は取り込み成功時点でディスクに存在する。本文編集を破棄しても削除しない。手動で未使用画像を確認・削除できる。

### 17.3 既存画像の表示検証

- 取り込み時の検証済み状態を、外部配置されたファイルへ流用しない。プレビュー・cover・メディア一覧でデコードする前に、存在・実体形式・サイズ・画素・対応形式・固定安全上限を確認する。
- 拡張子偽装、SVG等の非対応形式、異常ヘッダー、上限超過は表示しない。ファイル自体は保持する。
- 検証キャッシュは内容識別子と検証ルール版へ結び付ける。mtime・サイズだけで差替えなしと判断しない。
- 原本保存と表示用処理を分離する。原本を変更せず、必要に応じた縮小表示用資源を生成できる。縮小生成の前段にもデコード予算を適用する。
- 一覧では原寸の大量デコードをしない。重い画像はプレースホルダーと手動表示操作を提供する。
- アニメーションは初期版プレビューで自動再生しない。静止フレームの安全な取得が証明できる場合だけ表示し、できなければプレースホルダーとする。全フレーム展開を検証手段に使わない。
- アニメーションのフレーム数等の固定上限は第34章に従う。環境上測定できない場合に無制限として扱わない。
- 画像リソース・ImageBitmap等の寿命も管理し、オブジェクトURL解放だけをメモリ解放の証拠としない。

## 18. 画像参照・削除

### 18.1 参照解析

- プレビューと同じMarkdown解析系から参照を抽出する。単純な文字列検索だけで未使用を判定しない。
- インライン画像・参照形式画像、ローカルメディアへのリンク、cover.srcを保護対象にする。
- コードブロック中の例示文字列は実参照とみなさない。
- URLエンコード・相対パス・フラグメント等を第16章と同じ規則で扱う。
- 対応外構文等で安全に判定できない場合は「参照状況不明」とし、未使用と断定しない。
- 保護範囲は当該記事の保存済み本文とcover。別記事・独自frontmatter内の参照は対象外であることを画面に示す。
- 対応外構文にメディア参照が含まれないと証明できない場合、当該記事全体の未使用判定を「参照状況不明」とする。構文単位に狭める最適化は、その保守性を試験で証明できる場合に限る。
- 解析の打切り・時間超過・読み取り失敗も参照不明とし、未使用画像の削除候補へ回さない。

### 18.2 削除

- 未保存編集がある間は画像削除を停止し、保存または破棄を先に選ばせる。確認・退避中に生じた後続編集と個別削除の確定工程は第11.3節に従い、保存済み本文の照合だけで編集中の新たな参照を無視しない。
- 保存済み記事で参照中の画像は通常削除禁止。先に参照を外して保存する。
- 参照不明の場合も初期版UIからの削除を停止し、外部ツールでの確認を案内する。
- 削除前に最新本文・cover・画像ファイルを確認する。確認時から変わっていたら再確認する。
- 対象パス、サイズ、Git状態、参照保護の範囲、復元制限を示す。第19.1節の検証済み退避を完了し、明示確認後に選択画像のみ削除する。
- 未使用画像を自動削除しない。

## 19. 記事削除・復元

- 未保存編集がある場合は削除を停止し、保存または破棄を先に選ばせる。削除確認開始から結果判定までは第11.3節に従い対象記事の編集を停止し、コピー・退避・UI応答を維持する。
- タイトル・ID・ファイル数・総容量・削除予定パス一覧を提示する。未知ファイル・隠しファイル・サブフォルダも省略しない。表示の仮想化は可能だが、列挙未完了のまま削除しない。
- Git管理済み、未追跡、無視対象、未コミット変更を区別する。Gitだけで未コミット内容を復元できると説明しない。
- 記事・画像のUIからの削除には、Git状態にかかわらず第19.1節の検証済み退避を必須とする。初期版に退避を省略する高速削除は設けない。
- 確認時・退避検証時・削除実行直前のファイル集合と内容を照合する。検出した追加・変更・種類変更があれば停止して再確認する。
- 再帰処理の予算は第34章に従う。対象を列挙・検証できない場合は削除しない。
- 記事フォルダ全体を対象とし、未知ファイルも含むことを明示する。実行は確認済みの対象を個別に扱い、再帰一括削除だけに依存しない。未知の追加ファイルを検出したら止める。
- 一部削除後に失敗した場合、削除済み・残存・不明を区別し、成功と表示しない。再走査の上、残存対象に対して再確認する。
- 削除記事はGit変更一覧に表示し、当該記事の削除をまとめてコミットできる。タイトル等は取得可能ならHEADから表示し、取得不能ならIDを使う。
- CMS独自のリポジトリ内ゴミ箱と、自動復元は設けない。退避からの復元・Gitからの復元は外部ツールで行い、再読み込み後に検証する。
- 外部プロセスが実行中に書き換える競合の完全防止は保証しない。外部書き込み禁止運用と、第35章の保証境界を示す。

### 19.1 削除前退避

1. ユーザーがリポジトリ外の退避ディレクトリを明示選択し、権限を付与する。退避先を自動作成・自動探索しない。iOS・iPadOSでは第38.1節の退避領域を用いる。
2. 選択リポジトリと同一・配下・祖先等の危険な重なりがないことをハンドルの同一性・相対解決等で確認する。少なくとも退避物が削除対象やCMS走査へ混入しないことを証明する。証明不能なら停止する。
3. 操作別の新規退避フォルダを作成する。既存フォルダ・既存ファイルを無確認に再利用しない。新規所有確認は第5.3節に従う。
4. 確認済みの通常ファイルをバイト列のままコピーする。空ディレクトリも記録する。間接参照・特殊ファイルがあれば停止する。OS固有属性を保存できない場合は事前に表示し、復元可能範囲を限定する。
5. 相対パス、種類、サイズ、SHA-256等の暗号学的ハッシュ、操作日時、アプリ版を含むマニフェストを作る。元の絶対パスや機密情報を不必要に含めない。
6. 退避先を再読み込みし、内容・集合を検証する。元側も再照合し、検出した変更があれば削除へ進まない。
7. 「退避検証済み」と場所・容量・検証時刻を表示し、削除の最終確認を求める。
8. 削除後も退避は保持し、自動削除しない。保存期間・外部媒体へのコピーはユーザーが管理する。残骸・途中失敗先を表示し、自動掃除しない。

ダウンロードを開始しただけでは、保存先へ正しく保存されたと検証できないため、この退避要件の代替にならない。退避は別ディスク・別媒体上のバックアップや耐電断性まで保証しない。削除時の退避と、日常的なバックアップを区別する。

### 19.2 退避からの手動復元案内

- マニフェストと退避先を開くための案内、復元対象の相対パス、外部ツールで戻した後の確認手順を提供する。
- 元フォルダに新しいファイルがある場合は上書きを推奨せず、別場所で内容を確認するよう案内する。
- 復元後はID一致・slug・画像参照・Git状態を再検証する。CMSが復元を実行していないのに「復元完了」と表示しない。

## 20. ローカルGit機能と互換性

### 20.1 機能範囲

対応：既存対応リポジトリの読み込み、明示的なgit init、ブランチ・変更一覧、記事単位のステージングとコミット、履歴表示。GitHubのREST APIによるpush・pullと、同期時の簡易マージ・競合解決（第40章）。

対象外：Gitの通常の通信によるclone・fetch・pull・push、GitHub以外のホストとの同期、CORSプロキシ、ブランチ作成・切替、第40.5節以外のマージ、rebase、変更破棄、過去状態への復元。

保存時に自動コミットしない。Git未使用フォルダでは編集機能を維持し、Git操作時に初期化を案内する。git initは既存.gitエントリーがないことを確認してから行い、失敗時は残存状態を表示する。

### 20.2 初期版の書き込み対応条件

以下をすべて満たす構成のみGit書き込みを許可する。

- 選択ルート直下に通常の `.git/` ディレクトリがある非bareリポジトリ。
- 選択ルートが作業ツリーのルートである。
- 通常ブランチ上。detached HEADは書き込み非対応。
- merge・rebase・cherry-pick・revert・bisect等の進行中状態がない。
- 未解決indexエントリー、外部ロック等の処理中状態がない。
- submodule・worktree・sparse checkout等の特殊構成に依存しない。
- 対象記事にシンボリックリンク・特殊ファイル・CMSが保存できない属性の変更がない。
- 対象記事がGit LFS・必須フィルター・working-tree-encoding等、未対応の変換に依存しない。
- リポジトリ内で観測可能な署名要求・フック・フィルター等について、CMSが満たせない条件を検出したら停止する。
- OSグローバル設定、サーバー側規約、組織ルールをすべて検出できるとは主張しない。初回Git利用時に、CMSは署名・フックを実行せず外部の条件適合を保証しないことを説明し、利用可否の確認を求める。ユーザー確認で観測済みの危険条件を無効化できない。
- オブジェクト形式・index形式等が採用Git実装の検証済み対応範囲内。

上記を安全に判定できない場合もGit書き込みを止める。.gitがファイルの構成や親ディレクトリのリポジトリを権限領域外へ辿って開かない。任意のシェルコマンド・Gitフック・フィルターを実行しない。

### 20.2.1 Git由来パス・特殊index・設定

- Git設定、ref名、object参照、indexパスを未信頼入力として扱う。Git用パス検証と実フォルダ境界検証を両方行う。
- configのinclude／includeIf、objects/info/alternates、commondir、gitdir等の外部参照を追跡しない。対応を証明できない関連構成はGit書き込み停止とする。親・OSグローバル設定も参照しない。
- 不正ref名、逸脱パス、絶対パス、OS固有表現、大文字小文字・Unicode正規化で衝突するパスを拒否する。通常の日本語名を一律禁止するのではなく、実OSとの対応を検証する。
- indexのintent-to-add、skip-worktree、assume-unchanged、競合ステージ、拡張を含め、開始前状態を認識する。未対応フラグ・形式で安全な算出ができなければGit書き込み停止。
- 「既存ステージなし」は単なるstatus表示の空判定ではない。HEADとindexの内容差、追加予定状態、競合、未対応状態を調べ、対象を明示する。
- 対応外条件は観測可能／観測不能に分ける。観測不能な外部運用ポリシーを「違反なし」と表示しない。

Gitのindex・config・packed-refs・loose ref等、object以外のメタデータにも第34.5節の読込・解析・列挙予算を適用する。上限超過・解析不能を「既存ステージなし」「対応構成」とみなさず、Git書き込みを停止する。安全な記事編集の可否は独立判定する。

### 20.3 非対応時の扱い

Git互換性の理由だけなら、Git書き込み停止と記事編集停止を分ける。ただし未解決競合、未対応フィルターが必要な対象ファイル等、安全な編集ができない理由がある記事は読み取り専用にする。理由・影響範囲・外部ツールでの対処を表示する。

Git LFS等のファイルを通常画像と誤認して扱わない。.gitattributesを黙って変更しない。改行・属性・無視規則・ファイルモードについて、対応可否と試験結果を互換性表に記録する。ネイティブGitと同一挙動を未検証のまま称さない。

## 21. コミット契約

### 21.1 対象と事前条件

| 項目 | 仕様 |
| --- | --- |
| 操作単位 | 1記事フォルダの追加・変更・削除 |
| 未保存編集 | 先に保存または破棄を案内し、コミットしない |
| 対象外 | 他記事、設定、配布HTML、記事外ファイル |
| 既存ステージ | 開始前に存在する場合、またはindex状態が不明・未対応の場合は停止。解除しない |
| メッセージ | 必須。空白だけは禁止。編集可能な初期値を用意 |
| 初期値例 | `記事を更新: 記事タイトル` |
| コミット対象なし | その旨を表示し、空コミットしない |
| 無視対象 | 自動的に強制追加しない。対象外と理由を表示 |

記事の変更対象は実ファイルとHEAD・indexから算出する。削除記事もHEAD・indexのパスを使って識別する。対象パスの逸脱・別記事混入を防ぐ。

### 21.2 作成者とコミッター

- リポジトリローカルのuser.name・user.emailを使用する。OSのグローバルGit設定は自動参照しない。
- 未設定なら入力を求める。一時入力で今回のみ利用できる。
- 作成者とコミッターは同じ名前・メールとする。別指定・履歴の作成者偽装・amendは初期版対象外。
- リポジトリへの設定保存は別の明示操作とし、キー・値を確認させる。他の設定を壊さない。
- 設定保存失敗でもコミットが成功したと混同しない。

### 21.3 確認・実行

確認画面に対象記事、追加・変更・削除別の全対象ファイル、無視対象、メッセージ、作成者・コミッター、現在ブランチを示す。

実行直前にHEAD・index・対象ファイルを再確認する。確認時から変更されていれば停止し、再確認する。外部Gitの同時実行は禁止運用とし、ロック検出時は停止する。

### 21.4 失敗・再試行

- 開始時のHEAD・index、今回の対象・内容、生成できたコミットIDを操作中に保持する。
- 今回CMSが作ったステージと、開始前・外部由来のステージを区別する。
- ステージ成功後にコミットが失敗した場合は、ファイルを保持し、残ったステージと理由を表示する。コミット中に継続した本文編集は未保存の編集として別管理し、今回コミットへ混入させない。
- 同一セッション内の再試行は、HEAD・index・対象内容が今回の予定と一致する場合に限り、確認後に許可する。
- 状態が違う、再起動で由来が不明、外部変更がある場合は通常の既存ステージとして停止し、外部Gitでの確認を案内する。
- 自動ステージ解除・自動リセット・変更破棄をしない。
- UI更新だけ失敗した可能性がある場合、既知コミットID・HEAD・親・対象ツリー等を照合して実際の成功を確認する。判定不能なら結果不明として停止する。
- 成功確認なく同じ操作を再実行して、重複コミットを作らない。

## 22. Git状態・履歴表示

- ブランチ名、Git書き込み可否、停止理由、変更一覧を表示する。
- ステージ済み・未ステージ・未追跡・削除・競合・無視対象を区別する。無視対象は必要時に展開する。
- 履歴はリポジトリ全体と選択記事のパスに限定した表示を切り替えられる。
- 初回50件、追加50件単位で表示する。ただし内部走査量の上限とは区別する。1回の取得は調査コミット数・ツリー数・時間・メモリの予算を持つ。
- 予算内で50件に達しない場合は、取得済み分と「未調査あり」を表示し、継続カーソルから追加調査する。「履歴なし」と断定しない。
- 調査のキャンセル、進捗、再開を提供する。初期一覧表示に記事別履歴走査を混ぜない。
- コミットID、日時、作成者、メッセージを表示する。
- 記事履歴は現在のIDパスを対象とし、手動改名・衝突解消前の別パスを自動追跡しない。
- 初期版に高度な差分ビュー、履歴からの復元・変更破棄は設けない。外部変更時の3版の軽量差分は提供する。

## 23. 一覧・検索・再読み込み

| 項目 | 仕様 |
| --- | --- |
| 主な表示 | タイトル・状態・タグ・更新日時・公開日時 |
| 補助表示 | ID、未保存、未コミット、検証エラー、権限・不完全状態 |
| 空タイトル | 「無題」とID |
| 初期順 | updatedAt降順 |
| ソート | 作成日時・更新日時・公開日時・タイトル、各昇順／降順 |
| 不正・未設定日時 | 昇順・降順とも末尾。不正値に警告 |
| 同値 | 記事IDのコードポイント昇順を第2キー |
| キーワード | タイトル・slug・ID・タグへの部分一致。英字大小を区別しない |
| 本文検索 | 初期版対象外 |
| 状態フィルター | すべて／下書き／公開対象 |
| タグ | 複数指定、全タグを持つ記事に一致。選択タグの一致は大文字小文字を区別 |
| 条件結合 | キーワード・状態・タグをAND |

タイトルソートは日本語ロケールの照合を使用し、実装・環境依存差を許容するが、同一環境の同値順は安定させる。未来のpublishedAtは「公開予定日時」を補助表示する。一覧の状態はサイトへの配信完了を示さない。

### 23.1 検索・一覧の入力支援

- キーワードは英字大小を区別しない部分一致、タグ選択は保存値の完全一致であることをUIで区別する。
- タグ入力は既存タグの候補を提示するが、大小文字・空白を無断で統合しない。確定前に前後空白を可視化する。
- 一覧行、タグ候補、削除・複製対象一覧は仮想化またはページ分割し、全件DOM化を避ける。件数・総数・フィルター結果が省略で誤認されないようにする。
- メタデータ未取得、検査不能、検索結果なしを別状態として表示する。

### 23.2 再読み込み範囲

- 現在の記事：未保存確認後にディスク版を読み込む。
- 一覧：現在記事の編集内容を保持したまま索引を更新する。現在記事の外部変更は通知し、編集中内容へ上書きしない。
- Git状態・履歴：記事の未保存編集を保持して再取得する。
- フォルダ全体：未保存確認と進行中操作の終了後に行う。

自動ファイル監視は提供しない。最終読み込み時刻と更新中状態を示す。一覧走査失敗は記事単位で記録し、不完全な検索・重複検査を完全な結果として表示しない。

## 24. 既存記事の検証

| 状態 | 処理 |
| --- | --- |
| 正常 | 通常編集可 |
| frontmatterなし・構文エラー・キー重複 | 原文で修正。検証通過まで保存不可 |
| 必須項目不足・型不正 | エラー箇所を表示。勝手に補わない |
| ID不一致 | 通常保存停止。第10章の専用修正 |
| ID長が設定と異なる | 7〜32文字の有効IDなら許容 |
| ID文字種・長さ不正 | 閲覧・コピーのみ。外部修正 |
| slug不正・当該slugの重複 | 保存停止 |
| status不正 | draftまたはpublishedへの修正を要求 |
| 画像参照切れ | 警告するが記事保存可 |
| 画像参照の領域逸脱 | プレビューで取得しない。coverは検証エラー。本文原文は保持 |
| 未知フィールド | 対応YAML範囲内なら保持 |
| 非対応YAML・上限超過 | 読み取り専用、コピー・外部修正案内 |
| index.mdなし | 不完全記事として表示 |
| 未解決Git競合 | 対象記事の通常編集・保存を停止 |

エラーはファイルパス、項目、原因、可能なら行・列、対処を表示する。競合マーカーだけで競合と断定せずGit状態と照合する。Git未使用時の疑わしいマーカーは警告するが、本文例示を一律保存禁止にしない。

### 24.1 修復保存の方針

- 初期版は「不正値を残したままの制限付き修復保存」を設けない。保存時は当該記事の完全なスキーマ検証を通す。
- 本文・タイトルのみの変更でも、当該記事の既知の不正slug・重複等は修正が必要。他記事由来の検査不能が無関係な保存を一律停止しない範囲は第7章に従う。
- UI内で修復可能：対応範囲のYAML構文、必須値・型、status、slug、tags、cover、専用操作によるID不一致・不足／不正createdAt。
- 外部修正が必要：不正UTF-8、ID文字種・長さ不正、非対応YAML、資源上限超過、Git競合、対応外フィルター等。
- 修復操作では勝手な値補完をしない。自動補正を提案する場合も差分と確認を必要とする。
- 各エラーに、CMS内で直せるか、保存できない理由、具体的な外部修正手順、編集中原文の退避を提示する。
- 他記事のエラーは記事単位に隔離し、一覧や無関係な編集を停止しない。

## 25. 規模・性能・応答性

### 25.1 初期検証データ

| セット | 条件 |
| --- | --- |
| B：基本 | 1,000記事、本文各約10 KiB、メディア総量1 GiB・約1,000ファイル、Git履歴100コミット |
| L：本文境界 | 1／3／5 MiB本文、巨大な1行、表、コード、参照リンク、frontmatter上限・深度境界 |
| F：ファイル多数 | 1記事に10,000エントリーまで、空ディレクトリ、小ファイル、深さ境界・超過 |
| H：長い履歴 | 10,000コミット、対象記事の変更がまばらな履歴、他記事中心の履歴、pack済み・loose双方 |
| M：画像境界 | 40M画素、表示上限超過、異常ヘッダー、アニメーション、偽装形式、既存外部配置 |
| E：不正混在 | 10%以上の不正・読み取り不能・不完全記事、重複slug、対応外Git構成 |
| R：長時間 | 2時間の入力、200回の記事切替、100回の画像表示と破棄、Undo/Redo反復 |

- 実際の分布・総バイト数・ファイル数・コミット配置を固定し、生成手順またはフィクスチャを保存する。
- 記事数・総容量はハード制限ではないが、B超過規模の通常応答保証は別承認なしに称さない。安全予算と停止動作は超過時にも適用する。
- 記事ファイル5 MiB超はフォーム・原文の対話編集・全文プレビューすべて対象外とする。無制限全文読込をせず、メタデータの有界読込と一覧警告、外部編集案内を提供する。元ファイルのコピーは有界ストリーム処理で行う。
- frontmatter 1 MiB上限は別途適用する。

### 25.2 読み込みとUI

- 一覧メタデータを優先し、画像実データ、プレビュー、Git状態・履歴を段階取得する。
- frontmatterは区切りまで有界読み込みする。全記事本文を初期一覧のために保持しない。
- I/O、CPU解析、画像デコードの並列度を分ける。初期値はメタデータI/O最大8、CPU重処理最大1、画像検証・デコード・保存最大1とし、測定による変更は記録する。
- 重い解析・ハッシュ・差分・Gitは終了可能な隔離処理または分割処理で行う。取消要求を長時間同期ループで無視しない。
- キャッシュ、Undo、画像資源、AST、DOMの予算と破棄契機を第34章に従って管理する。
- 保存・Git・画像処理で入力を妨げない。編集停止時間を個別に測定する。

### 25.3 性能合格値の確定手順

- 技術ゲートで測定環境を固定する。Windows・macOSの代表的なノートPCを各1台以上、メモリ8 GiB・ローカルSSD級の最低検証構成を含める。具体CPU・OS・ブラウザ・空き容量・電源条件を記録する。
- 第34.1節の数値を、実測前に置く初期製品目標とする。実測結果そのものを自動的に合格値にしない。
- 初期一覧、検索、記事切替、保存、取り込み、Git状態・コミットについて計測区間、データ条件、コールド／ウォーム、反復回数、中央値、p95、最大値、UI応答、ピーク・定常メモリを記録する。
- UI主要操作は原則30反復以上。コールド起動・長時間試験等で異なる回数を使う場合は事前に記録し、少数標本のp95を過大解釈しない。
- Bは通常応答目標を満たすこと。境界セットは通常と別クラスで測定し、予算超過でもUI・キャンセル・退避が使えること。
- 目標を満たせない場合は方式・対象規模・機能を見直し、理由と影響を再承認する。測定後の都合のよい緩和や、未確定のままの受け入れ完了は禁止。
- アプリのメモリ測定はプロセス・Worker・描画資源を含め、APIで測れない部分と測定ツールの限界も記録する。

## 26. 受け入れ試験

各試験について環境、事前条件、操作、期待するUI・ファイル・Git状態、実測結果を保存する。正常系のみでは合格にしない。

### 26.1 起動・基本機能

- A01：Chrome・Edge、Windows・macOSで、サーバー・CDN・自動通信なしに起動する。
- A06：iPhone・iPadのSafariとホーム画面で、配布物の取得以外の自動通信なしに起動し、オフラインでも起動する。
- A07：iOS・iPadOSで作業場所の作成・取り込み・書き出し・削除ができ、書き出したzipをデスクトップ版で開ける。
- A08：iOS・iPadOSで解錠前に記事・名前・トークンが読めず、回復コード・パスフレーズ・パスキーのそれぞれで解錠できる。
- A02：権限拒否・失効・フォルダ再選択で編集内容を失わない。
- A03：記事・画像の保存後、再起動して再編集できる。
- A04：保存データを別のフロントアプリで読み、規定の公開条件・相対画像参照を扱える。
- A05：設定欠落・部分不正・構文不正・未知版・同名ファイル障害の停止範囲が第4章どおり。

### 26.2 データ保持

- D01：開いて保存するだけでは書き込み・updatedAt更新をしない。CRLF文書でも同様。
- D02：frontmatterのみの変更で、LF統一・BOM除去以外の本文変更がない。
- D03：未知の入れ子値、巨大整数、コメント、キー順、引用符・フロー配列等の保持フィクスチャを通過する。
- D04：本文・標準値・未知値・コメントだけ・書式だけ・updatedAtだけの変更が第8章どおり。
- D05：不正UTF-8、非対応YAML、深い構造、frontmatter上限超過を黙って変換・保存しない。
- D06：標準項目不足、日時不正、重複キー、ID不一致の修正経路が意図どおり。

### 26.3 外部変更と失敗注入

- F01：外部で内容変更・削除・別エントリーへ置換した場合に保存停止する。
- F02：比較不能・権限失効・書き込み失敗・クローズ失敗で原文を退避できる。
- F03：書き込み後の検証失敗は成功表示せず、再試行で実状態を照合する。
- F04：新規作成・複製の各工程を中断し、不完全記事を正常記事と表示しない。
- F05：画像取り込みの失敗・一括キャンセルでファイルごとの結果が正しい。
- F06：記事削除の途中失敗で残存パスを表示し、再確認なしに追加削除しない。
- F07：操作中のフォルダ切替・連打・二重実行を防ぐ。
- F08：ブラウザ終了後に残存状態と復旧ドラフトを検出する。退避済み／未退避を区別し、ドラフトをディスクへ自動上書きしない。最後の未退避編集までは復旧を保証しないことも確認する。
- F09：別タブ検出の実測範囲と限界を記録する。完全排他の合格試験とはしない。

### 26.4 Git相互運用

- G01：外部Git作成→CMS変更・コミット→外部Gitで内容・履歴・整合性検証。
- G02：CMSでgit init・コミット→外部Git変更・コミット→CMS再読み込み。
- G03：記事・画像の追加・変更・削除、削除済み記事のコミット対象が正しい。
- G04：別記事・設定・開始前ステージ・無視対象を混入させない。
- G05：ステージ成功後のコミット失敗を注入し、今回ステージを区別して再試行する。
- G06：コミット成功後のUI更新失敗を注入し、重複コミットを作らない。
- G07：再起動後や外部変更後の由来不明ステージを自動解除しない。
- G08：worktree、submodule、detached HEAD、処理中状態、LFS・属性・フック・署名等の対応外構成で安全に停止する。
- G09：作者設定の一時利用・明示保存・設定保存失敗の扱いが正しい。
- G10：OS間の改行・パス・ファイルモードの互換性を対応表どおり検証する。

### 26.5 悪意ある入力・通信

- S01：javascript等の危険URL、生HTML、イベント処理を実行しない。
- S02：絶対パス、file URL、ドット区間、エンコードされた逸脱で記事外ファイルを読まない。
- S03：外部画像・ハイライト文法・フォント・解析等の自動通信を行わない。
- S04：タイトル・タグ・ファイル名・Gitメッセージ・エラー内容をHTMLとして解釈しない。
- S05：巨大YAML・深い構造・エイリアス・異常画像・過剰な一括投入を安全に拒否する。
- S06：参照形式画像、コード内の例示、URLエンコード、coverを正しく判定し、参照中画像を削除しない。
- S07：不正記事が混在しても無関係な正常記事を編集できる。

### 26.6 一覧・性能

- P01：1,000記事・1 GiB基本セットで、承認済み性能付表を満たす。
- P02：ファイル多数・本文大・履歴長・不正記事混在の別セットを測定する。
- P03：未設定・不正日時は昇順・降順とも末尾、同値順は安定する。
- P04：一覧再読み込みで現在の未保存編集を上書きしない。
- P05：一覧が古くてもslug検査時に最新状態を確認し、検査不能を重複なしと誤表示しない。

### 26.7 追加試験との関係

- 第37章T01〜T28もMVP必須試験とする。既存試験との重複は同じ実行結果を参照できるが、期待状態と注入点が満たされていることを確認する。
- S05の資源試験は第34章の各予算を網羅する。P01〜P02は第25章のB／L／F／H／M／E／Rセットへ対応付ける。
- IME・支援技術・復旧・退避は補助的な参考試験ではなく、受け入れ判定へ含める。

## 31. 実フォルダ用fsアダプターの契約（P0）

### 31.1 意味論の記録

アダプターは独立した実装・試験対象とする。採用Git実装の固定版が実際に呼ぶメソッドを抽出し、次の形式の表を完成させる。下表の「必要な記録」は合格済みの宣言ではない。

| 機能 | 必要な記録 | 禁止事項 |
| --- | --- | --- |
| readFile／有界読込 | バイト精度、UTF-8の扱い、存在・種類・権限エラー | 不正UTF-8の黙った置換、巨大ファイルの無制限全文読込 |
| writeFile | 切詰め時点、一時書込・close・再読込、abort後の実状態 | close前の成功表示、失敗時の元ファイル自動削除 |
| stat／lstat相当 | 時刻精度、サイズ、種類、リンク観測能力、属性 | 取得不能属性をネイティブ値のように捏造すること |
| readdir | 列挙範囲、順序、途中失敗、変更中の扱い | 列挙未完了を全件として扱うこと |
| mkdir／新規ファイル取得 | 既存との区別、所有確認根拠、競合窓 | create指定だけを排他作成成功と見なすこと |
| unlink／rmdir | 個別対象確認、空判定、途中失敗、外部追加 | 未確認ファイルを再帰一括で巻き込むこと |
| rename／置換相当 | 実装が必要とする意味、原子性の有無、失敗後状態 | コピー＋削除を原子的renameと称すること |
| ロック | 取得・保持・解放・残骸・別プロセスとの関係 | 存在確認だけを排他取得と称すること |
| mode／実行属性 | 読取・保持・変更できる範囲、indexへの反映 | 未対応属性変更を黙ってコミットすること |
| sync／永続化 | APIで確認できる範囲、非保証 | 耐電断・物理永続化の虚偽保証 |

- メソッドは「実現済み」「制限付き近似」「実現不能／未使用」に分類する。
- 近似はGitの呼出箇所ごとに安全性を証明する。関数名の一致だけでは互換性を認めない。
- アダプター内部の仮想時刻等が必要な場合、ネイティブGitの変更検出やindexとどう整合するかを記録する。
- `.git`へのアクセスはGit専用の許可範囲に閉じる。記事やメディアのパス解決から`.git`へ到達させない。

### 31.2 Git書き込みの観測と中断

- init、add、remove、commit、ローカル作者設定の各操作で、ファイルI/O列と意味上の確定点を記録する。
- object、index、HEAD、ref、reflog、config等、実際に更新するファイルの各書き込み前後・close前後で中断する。採用実装が更新しないものはその旨を記録する。
- 再起動後、既知のコミットID、HEAD、親、対象ツリー、index、作業ツリーを照合する。外部Gitで整合性検査を行う。
- objectだけ残った状態、indexだけ更新された状態、ref更新が不明な状態を区別する。未参照objectを自動掃除しない。
- 壊れた／由来不明のロックやindexを自動削除・自動再生成しない。外部Gitでの確認手順を提示する。
- 外部プロセスの完全排他を証明しない一方、単一CMS・外部書き込みなしの前提でも中断により未検出の破損や誤成功を起こさないことを必須とする。
- 必要な安全性をAPIで実現できない場合は、起動方式やGit方式の変更を再合意する。

## 32. 境界・間接参照・未信頼入力の追加契約

### 32.1 実ファイルと文字列の境界

- パス正規化とファイルシステム実体の検証を別工程として記録する。
- ルート選択がリンクを経由する場合と、選択済みルート配下のリンクを辿る場合を別々に試験する。
- macOSのシンボリックリンク、Windowsのシンボリックリンク・ジャンクション等を含む。利用可能な環境でのハードリンク等も、観測可能性と変更波及を検討する。
- 読込、プレビュー、複製、削除、退避、Git走査ごとに「拒否される」「通常エントリーとして見える」「判定不能」を実測する。判定不能を安全と扱わない。
- 大文字小文字、Unicode正規化、末尾の空白・ドット、予約名、区切り文字、二重エンコード、フラグメント、クエリの扱いを固定する。
- パスは1回の共通パイプラインで解釈し、表示検証と取得時で復号・正規化回数を変えない。曖昧な二重解釈は拒否する。
- 記事のmedia参照は、記事ルートとmediaハンドルから許可された相対セグメントだけを辿る。文字列接頭辞比較だけで領域内判定しない。
- 観測能力の不足が通常利用と衝突する場合は方式の問題として扱い、ユーザーに大量の判定不能停止を負わせて合格としない。

### 32.1.1 権限境界図とデータ経路

```text
ユーザー操作
    |
    v
CMS UI・単一正本文書・リビジョン
    | 固定したスナップショット／型付き要求
    +--------------------------+
    |                          |
    v                          v
権限保持層                  終了可能な解析層
    | 許可済みIDを再解決        | 有界データのみ
    | 書込み直列キュー          | YAML／Markdown／差分
    v                          v
選択フォルダ／Git          検証済み表示データ
    ^                          |
    | 記事由来の直接経路なし    v
    +-- X -- プレビュー層（無スクリプト・独立オリジン）

復旧ドラフト：同意したブラウザ内領域、ディスクへの自動反映なし
削除前退避：別途選択したリポジトリ外領域、検証完了後のみ削除可
外部リンク：親UIの確認操作からのみ開く、自動通信経路なし
```

- 図中の処理配置・プロセス・Worker数は設計記録で具体化する。論理的分離だけを独立したセキュリティ境界と称さない。
- メッセージの各種類に、許可送信元、最大サイズ、スキーマ、対象リビジョン、取消IDを定義する。古い解析結果が新しい文書へ適用されないことを保証する。
- 画像表示用資源の生成・寿命は親側で管理する。任意のblob URLを記事やメッセージから受け付けない。

### 32.2 通信試験と診断

- 起動、一覧、検索、原文、プレビュー、画像、Git、ドラフト、エラー表示の各工程で自動通信ゼロを検査する。
- 記事由来の画像、CSS、フォント、リンク先読み、フォーム、iframe、埋込み、Worker等の経路を試験する。
- 通信試験はオフラインで動くことだけでなく、オンライン状態でも要求を発生させないことを確認する。
- 診断ログは既定でローカルメモリ内の件数・工程・エラー種別に限定する。本文・メール・絶対パス等の採取は必要性を限定し、出力前にプレビュー・マスキング・削除が可能であること。
- ログ、マニフェスト、復旧ドラフトも未信頼入力として再読込時に検証する。

## 33. ブラウザ内復旧ドラフト（P1）

### 33.1 目的と同意

- リポジトリ保存とは独立した、未保存編集を失いにくくするためのローカル退避機能とする。
- 初回利用時に、保存先がブラウザ内部であること、内容、保持期間、削除方法、共有端末上の注意、復旧の限界を示す。「有効にする」を推奨するが、同意前に本文を永続保存しない。
- ユーザーは無効化できる。無効時は「復旧退避なし」を常時表示する。ユーザーが無効にした状態と、技術的に機能が成立しない状態は区別する。
- 対応環境で機能を提供できることはMVP要件。利用不能環境では原文の手動退避を案内するが、それだけでゲート合格にしない。
- デスクトップでは暗号化・OSユーザー間の秘密保護を保証しない。ブラウザプロファイルへアクセスできる者に読まれる可能性を説明する。iOS・iPadOSでは第39章の暗号化を適用する。自動送信・同期はアプリとして行わない。
- iOS・iPadOSでは復旧ドラフトと作業場所が同じ保存領域にあり、ストレージ消去への備えにならないことを説明する（第38.4節）。

### 33.2 保存内容と識別

- 保存内容：編集中原文、記事IDまたは未保存記事の一時ID、編集リビジョン、元ファイルの内容ハッシュ、退避時刻、アプリ・ドラフト形式版、内容チェックサム。
- 画像原本・Gitオブジェクト・リポジトリ全体は保存しない。未保存新規記事も対象とする。
- 保存済み記事の基準本文を恒久保存することは必須としない。基準ハッシュと、復旧時に確認できるディスク状態から競合を判断する。基準本文がない場合は3版比較ができないことを明示する。
- ワークスペースはランダム識別子で管理し、絶対パスをキーへ埋め込まない。フォルダ名や記事IDだけで同一フォルダと認定しない。
- 次回選択フォルダとの照合方式を固定する。ハンドルを永続化する場合は事前に説明し、識別用保存が次回の書き込み認可を意味しないことを明示する。
- 同一性が確認できない退避は「関連先未確認」とし、ユーザーが原文を確認・退避できるようにする。別記事へ自動適用しない。

### 33.3 更新・容量・失敗

- 有効時は入力が2秒停止した時点を目安に退避し、連続入力中でも最大10秒ごとに退避を試みる。IME変換中の未確定入力は壊さず、確定済みスナップショットまでを扱う。
- 初期予算：1記事につき最大2世代、1ワークスペース最大20記事、全体50 MiB。最新原文を優先し、古い世代の整理でも最新未保存ドラフトを黙って追い出さない。
- 原則保持期間は最終退避から7日間。期限と削除方針を初回説明・一覧に表示し、期限後にアプリが次に起動した際に整理する。保存され続けることも、正確な時刻での消去も保証しない。
- 容量超過時は退避停止と対象を表示し、退避書き出し・ユーザーによる削除を案内する。未退避状態を「退避済み」と表示しない。
- 実際にブラウザストレージへ保存し、検証できたリビジョンだけを退避済みとする。権限、quota、プライベートモード、削除・破損等の失敗を表示する。
- 期限整理以外の最新未保存ドラフト削除は、保存済み／明示破棄／ユーザー削除のいずれかを条件とする。整理操作の意味を区別する。
- リポジトリ保存が成功しても、後続編集リビジョンのドラフトを削除しない。破棄済みリビジョンの再提示を防ぐ。

### 33.3.1 非同期退避と破棄・保存・無効化の順序

- 各退避要求にワークスペース・記事・編集リビジョン・要求世代を結び付ける。完了順を最新性の根拠にせず、古い要求の遅延完了が新しいドラフトや退避状態を巻き戻さないこと。
- 編集の明示破棄、ドラフト削除、期限整理、リポジトリ保存成功、機能無効化は、処理中・待機中の退避要求との順序を管理する。破棄・削除済みの世代を古い要求の完了で復活させず、保存成功前の要求が保存済み世代を未保存候補として復活させない。保存後の編集世代は独立して保持する。
- 無効化は以後の新規退避要求を止め、既存の未完了要求を取消または完了待ち等で確定させてから完了表示する。既存ドラフトを保持するか削除するかは専用UIで明示し、無効化と削除を同義にしない。無効化完了後に古い要求が本文を新たに永続保存することを禁止する。
- 世代番号、破棄済み記録、条件付き更新、トランザクション等の方式は採用ストレージに応じて確定する。UIで完了通知を無視するだけでは不十分とし、再起動後の永続状態でも復活・巻戻りが起きないことを実証する。方式・原子性の範囲・中断点をTG10へ記録する。
- 保存・破棄・削除・無効化の競合整理に失敗した場合は、成功を推定せず、対象と未確定状態を表示する。未保存原文の手動退避を提供し、確認できない削除や無効化を完了と表示しない。


### 33.4 復旧

- 起動・フォルダ選択後に退避候補を提示し、時刻、記事、基準ハッシュ、ディスクとの一致／相違／未確認を表示する。
- 「編集として開く」「原文を退避」「削除」を提供する。ディスクへは自動上書きしない。
- ディスクが基準版から変わっている場合は外部変更として扱い、比較・コピー・再編集を案内する。
- ドラフトのチェックサム・形式・長さを検証する。破損時は可能な範囲の原文救出と原因表示を行い、元記事を変更しない。
- アプリHTMLの移動・改名・更新、ブラウザプロファイル変更、ストレージ消去による識別や永続性の差を試験する。更新前の手動退避手順を提供する。
- 復旧できるのは実際に退避成功した範囲まで。クラッシュ直前の編集、ストレージ消去後、未同意・無効状態の復旧を保証しない。

### 34.2 入力・解析・描画の固定安全予算

値は初期版の固定値。リポジトリ設定で緩和できない。これらの積算で、単純なファイルサイズ以内でも制限することがある。

| 対象 | 初期予算 | 超過・検査不能時 |
| --- | --- | --- |
| 記事ファイル | 5 MiBまで対話編集 | 原文を無制限に読み込まず外部編集案内 |
| frontmatter | 1 MiB、深度50、ノード50,000、マッピングキー合計20,000、単一スカラー256 KiB | 読取専用。本文の通常編集も開始しない |
| YAML解析 | 1処理2秒 | Worker等を停止しエラー・原文退避 |
| Markdown | AST 200,000ノード、入れ子100、リンク・画像合計10,000 | 全文プレビュー停止。原文編集は範囲内で継続 |
| Markdown解析 | 1処理2秒 | 中断し軽量表示。古い版を現行と表示しない |
| プレビューDOM | 20,000要素 | 全文DOM化せず、部分表示またはプレビュー停止を明示 |
| コードハイライト | 1ブロック100 KiB、1行16 KiB、合計512 KiB、1要求500 ms | プレーンコードへフォールバック |
| 原文差分 | 各入力1 MiB、各20,000行、処理2秒、描画2,000行 | メタデータ差分・概要と各原文の退避 |
| メタデータキャッシュ | 原文全文を除き32 MiB | LRU等で再取得可能な情報から破棄 |
| Undo/Redo | 現在記事の履歴差分20 MiBまたは1,000操作の先到達 | 古い履歴を通知して切捨て。現文書は保持 |

- AST・ノード数の上限は、木をすべて作った後だけでなく構築中に適用する。対応不能パーサーの採用は資源試験で安全性を証明するまで不可。
- 字句解析前の深度爆発等も試験する。時間制限を同じイベントループの実行後判定だけで実装しない。
- 巨大文書をDOMへ隠して保持する方式で予算を回避しない。仮想化と全文解析の予算は別管理。

### 34.3 画像予算

| 対象 | 初期予算 |
| --- | --- |
| 1画像の固定バイト上限 | 100 MiB。取り込みはユーザー設定との小さい方 |
| 1画像の固定画素上限 | 40,000,000。設定上限がそれ以上でも表示・デコードでは緩和しない |
| 同時デコード | 1ファイル |
| 保持中のデコード画像 | 合計80,000,000画素までを目安に、実測メモリと併せて制限 |
| アニメーション構造検査 | 最大200フレーム、累積100,000,000画素。全展開せず検査可能な場合に限る |
| プレビューの同時画像要素 | 最大50、画面外は遅延表示・資源解放 |
| 画像処理要求 | 30秒で成功または打切り・プレースホルダー確定 |

- アニメーションの構造・累積負荷を安全に確認できない場合は、取り込みまたは表示の該当工程を拒否する。未知を無制限扱いしない。表示は静止フレームのみ。
- 上限内でもブラウザデコーダーの内部メモリを完全には制御できない。ヘッダー検査、直列化、表示資源制限、異常画像試験を組み合わせる。
- 画像検査のために主UIを長時間同期停止させない。デコード中断ができない環境では隔離・前段拒否を含めて技術ゲートを判定する。
- 成功画像を本文へ挿入しなかった場合も、メディア管理で確認できる。編集破棄で自動削除しない。

### 34.4 再帰・Git・メモリ予算

| 対象 | 初期予算 | 超過時 |
| --- | --- | --- |

| 1回の列挙工程 | 10秒 | 中断・継続検討を表示。未完了で削除不可 |
| 大容量コピー・ハッシュ | 1 MiB以下のチャンクを基本、定期yield | 進捗と安全境界で取消。全量メモリ保持しない |
| 履歴1回の内部走査 | 1,000コミット、10,000ツリー、5秒の先到達 | 継続カーソルと未調査表示 |

- コピー・退避・大量コミットの全体時間を一律5秒にしない。チャンク単位の応答・進捗と、工程別の実測所要時間を管理する。
- pack圧縮後サイズだけで展開負荷を判定しない。展開中の上限とキャンセルを適用する。
- メモリ数値は測定上の受け入れ値であり、JavaScriptからプロセスの全割当を厳密制御する保証ではない。観測可能なカウンター、入力制限、終了可能な処理、実測を組み合わせる。
- 記事原文、基準版、候補、Undo、AST、DOM、画像、Worker転送コピーの増幅を含めて測定する。
- Rセット終了後、不要資源破棄と測定上の安定化を待ち、初期定常値との差が20%または50 MiBの大きい方以内であること。単発のGC時刻ではなく継続増加傾向も評価する。

- 既存規定と重なる場合は両方を満たす。記事数・総容量を一律の製品ハード制限に変更するものではないが、1要求の走査量・保持量は有界とし、継続・再取得・部分結果の仕組みを定義する。

| 入力・処理 | 全文取得前／列挙時に必要な上限 | 解析・保持に必要な上限 | 超過・検査不能時 | 新規数値の状態 |
| --- | --- | --- | --- | --- |
| cms.config.json | 1ファイルのバイト数 | 深度、ノード・キー・配列要素数、単一値長、解析時間・結果保持量 | 第4.2節の全体不正と同じ限定停止。既存記事編集を維持 | TG09で確定・承認必須 |

- 技術記録には、入力種別、入口API、読込前検査、構築中カウンター、停止時点、残存状態、UI影響範囲、回復操作、試験IDを対応付ける。未対応の入口・未確定セルを残して受け入れ完了としない。


## 35. 操作別の保証境界表（P0／P1）

共通前提：対応・検証済み環境、必要な権限、単一CMS、ディスク変更中の外部エディタ・Git書き込みなし。悪意ある記事は前提から除外せず、未信頼入力として扱う。前提違反を理由に、検出済みの変更や失敗を無視してよいわけではない。

| 操作 | 観測・判定根拠 | 保証 | 非保証 | 回復先 |
| --- | --- | --- | --- | --- |
| 一覧 | 有界frontmatter、列挙成否、索引版 | 読取失敗・未検査を明示、正常記事は独立利用 | 全件同一時点のスナップショット | 一覧再読込、記事単位エラー修正 |
| 保存 | 基準・ディスク・候補バイト、リビジョン | 検出済み外部変更を黙って上書きしない。再読込一致後だけ成功 | 比較後の外部競合完全防止、耐電断 | 3版比較、原文退避、実状態再照合 |

- 新規作成のcreatedAtは編集開始時刻を保持し、初回保存の再試行やドラフト復旧でも取り直さない。新規作成のupdatedAtは初回保存の最終候補生成時刻とする。複製のcreatedAt／updatedAtは最終index候補確定工程で取得した同一の時刻とする。実際の工程終了時刻との厳密一致は意味しない。再試行で新候補が必要な場合のみ、新規作成のupdatedAtまたは複製の両日時を再取得する。

- 操作ログはUI上の判断材料であり、永続トランザクションログの代替ではない。再起動後は実状態から判断する。

## 38. ブラウザ内の作業場所と取り込み・書き出し（iOS・P0／P1）

### 38.1 作業場所

- iOS・iPadOSでは実フォルダを扱わない。保存先はブラウザのOrigin Private File System（OPFS）内の作業場所とする。
- 作業場所の内部構成は第3章のリポジトリと同一とする。記事・画像・`.git`・`cms.config.json` の扱いはデスクトップと同じ規則に従う。
- 作業場所は複数持てる。作業場所ごとに乱数のIDを持ち、IDを領域名とする。表示名は暗号化して保持する（第39章）。
- 作業場所の作成・選択・削除は明示操作とする。削除は第19.1節の退避と同等の確認を経て、書き出し（第38.3節）または同期済み（第40章）であることを示してから行う。
- 削除前退避（第19.1節）の退避先は、作業場所の外の同一オリジン内の退避領域とする。ユーザーによる選択は求めないが、退避領域を作業場所の走査・削除対象に混入させない。退避領域はストレージ消去（第38.4節）から守られないことを表示する。
- 外部アプリによる作業場所の変更はない前提とする。別タブ・取り込み・pullによる変更は第12章の外部変更として検出する。
- OPFS用fsアダプターの意味論表を第31.1節と同じ形式で別に作る。`.git/config` 等への書き込み可否、`createWritable()` のclose時の反映、rename・ロック・modeの扱いを記録する。

### 38.2 取り込み

- 取り込みはユーザーが選んだzipファイル1つから新しい作業場所を作る。既存の作業場所へ上書き展開しない。
- zipは未信頼入力とする。絶対パス・`..`・空区間・制御文字・重複・大文字小文字とUnicode正規化での衝突を拒否する。第20.2.1節のGit用パス検証と第32章の境界検証を両方行う。
- 展開後の合計サイズ・件数・1件のサイズ・圧縮率に上限を設ける（第34.5節に入口として追加）。上限超過・解析不能では作業場所を完成扱いしない。
- 展開は完成マーカー方式とし、マーカー作成前の作業場所を正常表示しない。途中で止まった作業場所は不完全として表示し、自動削除しない。
- 取り込み後、第24章の既存記事検証と第20.2節のGit対応構成判定を通常のフォルダ読み込みと同じく行う。

### 38.3 書き出し

- 作業場所を `.git` を含めてzipにし、共有シートまたはユーザー操作によるダウンロードで端末の外へ渡す。
- 既定の書き出しは暗号化する（第39.4節）。平文のzipは確認を経て選べる。
- 書き出し前に、未保存の記事・未コミットの記事・未pushのコミットを表示する。
- ダウンロードや共有シートの開始だけでは、保存先へ正しく保存されたと検証できない。最後の書き出し日時は「書き出しを開始した日時」として表示し、検証済みバックアップと称さない。

### 38.4 ストレージの消去とバックアップ

- iOS・iPadOSのブラウザは、作業場所・復旧ドラフト・設定を含む同一オリジンの保存データを消去することがある。CMSはこれを防げないことを初回利用時と常時表示で示す。
- 起動時に `navigator.storage.persist()` を求め、結果と使用量を表示する。拒否・未対応の場合は「消去されることがある」状態として常時表示する。
- ホーム画面に追加したWebアプリとしての利用を推奨し、ブラウザでの利用時は推奨を表示する。
- 最後の同期（第40章）または書き出しより後に保存・コミットがあれば「端末の外にない変更あり（経過日数）」を常時表示する。一定日数（初期値3日）を超えたら起動時に同期または書き出しを促す。
- 復旧ドラフトは作業場所と同じ保存領域にあるため、ストレージ消去への備えにならない。第33章の説明にこれを含める。
- 配信元のオリジンが変わると保存領域は引き継がれない。配信元の移行は、旧オリジンでの同期または書き出しと、新オリジンでの取り込みまたはpullで行う。

### 38.5 配信

- iOS・iPadOS向けは単一HTMLをhttpsの固定オリジンから静的に配信する。マニフェストとService Workerによりオフラインで起動できる。
- 配布物以外の通信は第16.3節に従う。Service Workerは配布物のキャッシュだけを行い、記事データを扱わない。
- 配信される版を画面に表示する。新しい版の取得はユーザーの明示操作で行い、自動で切り替えない（第29.3節）。
- 開発版を他のページと共有されるオリジンに置く場合は、その旨を常時表示し、実データの利用を推奨しない。

## 39. 暗号化と解錠（iOS・P0）

### 39.1 対象と保証

- iOS・iPadOSの作業場所の内容（記事・画像・`.git`・設定）、ファイル名・フォルダ名、復旧ドラフト、GitHubのトークン、暗号化した書き出しを暗号化する。
- 保証：保存領域の内容を読んだ者が、鍵なしで記事・画像・名前・トークンを得られないこと。改ざん・差し替えを検出し、検出した項目を正常として扱わないこと。
- 非保証：保存領域の消去、CMSのページ自体の改ざん、解錠中の端末の操作、フォルダの木の形・ファイルの大きさ・更新日時・名前のおおよその長さの秘匿。GitHubへ送った内容は平文であり、リポジトリの公開設定に従う。

### 39.2 鍵

- 作業場所ごとにランダムなデータ鍵（AES-GCM 256bit）を作る。データ鍵は平文で保存しない。
- データ鍵は次の鍵でそれぞれ包んで保存する：パスキーのPRF拡張から導出した鍵、回復コードから導出した鍵（必須）、パスフレーズから導出した鍵（任意）。
- 回復コードは作成時に一度だけ表示し、保存しない。回復コードを失いパスキー・パスフレーズも使えない場合は誰も復号できないことを、作成時に説明し確認を求める。
- 回復コードはユーザー名・新しいパスワードの組のフォームで表示し、ブラウザのパスワード管理（iCloudキーチェーン等）に保存できるようにする。ユーザー名はロック中でも分かる作業場所IDから作り、解錠画面でも同じユーザー名で自動入力できるようにする。CMS自身は回復コードを保存しない。
- 作成時の回復コードの画面で、パスキーの登録を勧める。解錠画面ではパスキーを最初に示す。
- パスキーはサーバーへのログインではなく、端末内のデータ鍵を開く手段とする。RP IDは配信元のホスト名とし、配信元の移行時は登録し直す。
- 導出の方式・反復回数は技術ゲートTG14で確定する。

### 39.3 解錠とロック

- 起動時はロック状態とする。解錠後のデータ鍵はメモリにだけ保持する。
- 一定時間の無操作・ページの非表示でロックする（時間は設定可能）。未保存の編集がある場合は、ロック前に復旧ドラフトとして暗号化退避する。
- 復号できない項目（認証失敗）は読めない項目として件数・場所を表示し、上書き・削除しない。

### 39.4 暗号化の形式

- ファイル内容はファイルごとに書き込みのたびに乱数のIVでAES-GCM暗号化する。追加認証データに作業場所IDと平文の相対パスを含め、別パスへの差し替えを検出する。
- 名前は区間ごとに、親の平文パスと名前から導出したIVで決定的に暗号化する。名前の対応表は持たない。暗号化後の名前がOPFSの上限を超える場合の扱いをOPFS用fsアダプターの意味論表に記録する。
- 平文で行う検査（第20.2.1節のパス検証、Unicode正規化の衝突）は暗号化の前に行う。
- 暗号化した書き出しは、書き出しごとの鍵を回復コードまたはパスフレーズで包む。デスクトップ版CMSで取り込める。

## 40. GitHubとの同期と簡易マージ（P0／P1）

### 40.1 範囲

- 対応：GitHubのREST API（Git Data）による、1リポジトリ・現在のブランチのpush・pull、分岐時の記事単位の簡易マージ。iOS・iPadOS版とデスクトップ版の両方で提供する。
- 対象外：GitHub以外のホスト、Gitの通常の通信（smart HTTP）、CORSプロキシ、ブランチの作成・切替、rebase、force push、3本以上の分岐の合流。GitHub上の既存リポジトリの初回取得は、空の作業場所へのpullとして行う。
- 同期は明示操作でだけ行う。保存・コミット時に自動で同期しない。

### 40.2 認証

- 対象リポジトリ1つのContentsの読み書きだけを許した、有効期限つきのfine-grained personal access tokenをユーザーが入力する。
- トークンはiOS・iPadOSでは第39章の鍵で暗号化して保存する。デスクトップでの保存方法は技術ゲートで確定する。画面・ログ・診断情報に出さない。
- 通信先は `api.github.com` に固定する。

### 40.3 push

- リモートの先頭が手元の履歴にあることを確かめる。ない場合は分岐として第40.5節へ進む。
- リモートにないobjectをREST APIで作成し、作成されたコミットIDが手元のコミットIDと一致することを確かめてからrefを更新する。一致しなければrefを更新せず停止する。
- refの更新はforceなしで行う。拒否された場合は結果を再取得し、分岐として扱う。
- 更新後にrefを読み直して照合する。照合できない場合は結果不明として扱い、成功と表示しない。

### 40.4 pull

- 取得したobjectのIDを再計算して一致を確かめてから書く。第34.4節のGit予算を適用する。
- 作業ツリーの書き換えは、未保存・未コミットの記事がないことを確かめ、変わる記事の一覧を確認してから行う。書き換えの確定点と中断時の扱いを第36章に追加する。
- 外部変更（第12章）と同様に、書き換え前後の照合で予期しない変更を検出したら停止する。

### 40.5 分岐時の簡易マージ

- 共通の祖先を求め、祖先・手元・リモートをパスごとに比べる。共通の祖先がない（関係のない履歴）ときは空の tree を祖先とし、そのことを画面に示す。片側だけの変更はその側を採る。両側の同一変更はそのまま。両側で異なる変更、変更と削除の組は競合とする。
- 自動解決は記事の本文の行単位（変更範囲が重ならない場合）と、frontmatterのキー単位（片側だけが変えたキー）に限る。`id`・`createdAt` の食い違いは競合とする。画像・設定・その他のファイルは自動解決しない。
- 残った競合は記事ごとに、祖先・手元・リモートの3版と差分を示し、手元・リモート・編集した内容から選ばせる。すべて決まるまでマージコミットを作らない。
- マージの途中状態はCMS専用の場所に記録し、再開・中止できる。ネイティブGitのマージ状態ファイルは書かない。中止した場合は作業ツリー・index・refをマージ前に戻したことを照合する。
- マージコミットは第21章の契約に従って作成し、第40.3節でpushする。
- 第12.2節の「自動マージを提供しない」は外部変更の検出時の規則であり、本節の同期時の簡易マージには適用しない。
