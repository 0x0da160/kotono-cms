## 34. 性能・資源予算表（P1）

### 34.1 UI応答と通常性能の初期受け入れ値

下表は基本セットB・最低検証構成に対する製品目標である。未測定の達成宣言ではない。測定区間を固定し、失敗試行を集計から黙って除外しない。

| 操作 | 計測区間 | 初期合格値 |
| --- | --- | --- |
| 入力反映 | 確定済み入力イベントから編集表示の次描画 | p95 100 ms以内 |
| プレビュー追随 | 確定済み入力停止から表示更新 | 通常10 KiB記事でp95 300 ms以内。編集入力をブロックしない |
| 検索・フィルター | 索引済み条件確定から利用可能な結果描画 | p95 200 ms以内 |
| 記事切替 | 選択確定から本文・フォーム操作可能 | p95 500 ms以内。画像完了待ちは含めない |
| 初期一覧・先頭 | フォルダ認可済みの走査開始から先頭の操作可能行 | p95 1秒以内 |
| 初期一覧・確定 | 同上から全件索引の成否確定 | p95 5秒以内 |
| 通常保存 | スナップショット確定から再読込検証完了 | 10 KiB既存記事・全体再走査不要でp95 1秒以内 |
| slug再検査込み保存 | 保存要求から全体検査と保存確認完了 | p95 5秒以内。途中UI応答・進捗を維持 |
| Git状態 | 取得開始から基本セットの状態表示 | p95 5秒以内 |
| 通常コミット | 確認済み1記事10 KiB・画像変更なしの実行開始から照合完了 | p95 5秒以内 |
| 長時間処理の表示 | 処理開始から工程・進捗・取消可否が分かるまで | 300 ms以内 |
| キャンセル受理 | 操作から受理表示 | 1秒以内。安全境界までの停止時間は別表示 |
| 入力停止工程 | スナップショット固定等の入力不能区間 | 通常100 ms以内 |

- 画像取り込みは形式・画素・容量別に、検証／デコード／書込／再検証の時間を分けて記録する。20 MiB・40M画素境界の1ファイルは30秒以内に成功または打切り理由が確定すること。
- 大きな画像・本文・pack・長い履歴は通常性能と別クラスとし、固定予算内で中断・軽量表示できることを必須とする。
- 通信・権限のユーザー待ちは操作時間と別記録する。除外前後の値と理由を残す。

### 34.2 入力・解析・描画の固定安全予算

値は初期版の固定値。リポジトリ設定で緩和できない。これらの積算で、単純なファイルサイズ以内でも制限することがある。

| 対象 | 初期予算 | 超過・検査不能時 |
| --- | --- | --- |
| 記事ファイル | 5 MiBまで対話編集 | 原文を無制限に読み込まず外部編集案内 |
| frontmatter | 1 MiB、深度50、ノード50,000、マッピングキー合計20,000、単一スカラー256 KiB | 読取専用。本文の通常編集も開始しない |
| YAML解析 | 1処理2秒 | Worker等を停止しエラー・原文退避 |
| Markdown | AST 200,000ノード、入れ子100、リンク・画像合計10,000 | 全文プレビュー停止。原文編集は範囲内で継続 |
| Markdown解析 | 1処理2秒 | 中断し軽量表示。古い版を現行と表示しない |
| プレビューDOM | 20,000要素 | 全文DOM化せず、部分表示またはプレビュー停止を明示 |
| コードハイライト | 1ブロック100 KiB、1行16 KiB、合計512 KiB、1要求500 ms | プレーンコードへフォールバック |
| 原文差分 | 各入力1 MiB、各20,000行、処理2秒、描画2,000行 | メタデータ差分・概要と各原文の退避 |
| メタデータキャッシュ | 原文全文を除き32 MiB | LRU等で再取得可能な情報から破棄 |
| Undo/Redo | 現在記事の履歴差分20 MiBまたは1,000操作の先到達 | 古い履歴を通知して切捨て。現文書は保持 |

- AST・ノード数の上限は、木をすべて作った後だけでなく構築中に適用する。対応不能パーサーの採用は資源試験で安全性を証明するまで不可。
- 字句解析前の深度爆発等も試験する。時間制限を同じイベントループの実行後判定だけで実装しない。
- 巨大文書をDOMへ隠して保持する方式で予算を回避しない。仮想化と全文解析の予算は別管理。

### 34.3 画像予算

| 対象 | 初期予算 |
| --- | --- |
| 1画像の固定バイト上限 | 100 MiB。取り込みはユーザー設定との小さい方 |
| 1画像の固定画素上限 | 40,000,000。設定上限がそれ以上でも表示・デコードでは緩和しない |
| 同時デコード | 1ファイル |
| 保持中のデコード画像 | 合計80,000,000画素までを目安に、実測メモリと併せて制限 |
| アニメーション構造検査 | 最大200フレーム、累積100,000,000画素。全展開せず検査可能な場合に限る |
| プレビューの同時画像要素 | 最大50、画面外は遅延表示・資源解放 |
| 画像処理要求 | 30秒で成功または打切り・プレースホルダー確定 |

- アニメーションの構造・累積負荷を安全に確認できない場合は、取り込みまたは表示の該当工程を拒否する。未知を無制限扱いしない。表示は静止フレームのみ。
- 上限内でもブラウザデコーダーの内部メモリを完全には制御できない。ヘッダー検査、直列化、表示資源制限、異常画像試験を組み合わせる。
- 画像検査のために主UIを長時間同期停止させない。デコード中断ができない環境では隔離・前段拒否を含めて技術ゲートを判定する。
- 成功画像を本文へ挿入しなかった場合も、メディア管理で確認できる。編集破棄で自動削除しない。

### 34.4 再帰・Git・メモリ予算

| 対象 | 初期予算 | 超過時 |
| --- | --- | --- |
| 1記事の複製・削除・退避の列挙 | 10,000エントリー、深度32、通常ファイル合計2 GiB | 操作前に停止、外部ツール案内 |
| 1回の列挙工程 | 10秒 | 中断・継続検討を表示。未完了で削除不可 |
| 大容量コピー・ハッシュ | 1 MiB以下のチャンクを基本、定期yield | 進捗と安全境界で取消。全量メモリ保持しない |
| 履歴1回の内部走査 | 1,000コミット、10,000ツリー、5秒の先到達 | 継続カーソルと未調査表示 |
| Git object | 1オブジェクトの展開後64 MiB、1要求の展開累計256 MiB | Git操作停止。記事編集は独立判定 |
| Git pack | pack全量を無条件にメモリ保持しない | ストリーム／部分読込不能なら対応範囲を再検討 |
| CPU重処理の1要求 | 工程別上限を優先、未指定は5秒 | 安全境界で中断または処理失敗 |
| アプリ全体 | B定常512 MiB以下、境界セットのピーク1 GiB以下を初期性能目標 | 改善または方式・対象範囲を再承認 |

- コピー・退避・大量コミットの全体時間を一律5秒にしない。チャンク単位の応答・進捗と、工程別の実測所要時間を管理する。
- pack圧縮後サイズだけで展開負荷を判定しない。展開中の上限とキャンセルを適用する。
- メモリ数値は測定上の受け入れ値であり、JavaScriptからプロセスの全割当を厳密制御する保証ではない。観測可能なカウンター、入力制限、終了可能な処理、実測を組み合わせる。
- 記事原文、基準版、候補、Undo、AST、DOM、画像、Worker転送コピーの増幅を含めて測定する。
- Rセット終了後、不要資源破棄と測定上の安定化を待ち、初期定常値との差が20%または50 MiBの大きい方以内であること。単発のGC時刻ではなく継続増加傾向も評価する。

### 34.5 未信頼入力の入口別予算と未確定値の確定ゲート

- すべての未信頼ファイルに、全文取得前のバイト上限と、解析中の件数・深度・時間上限を定義する。列挙結果・解析結果・索引の保持量にも上限を設ける。個別規定のない入力を無制限として扱わない。
- 既存の第34.2〜34.4節の数値は維持する。下表で新規に必要となる数値は、TG09で固定フィクスチャと基本セットBを用いて提案・測定し、理由・影響・受け入れ試験とともに承認して本表または対応するリリース性能付表へ記録する。現時点では未確定であり、全対象の確定・承認・実証がリリース条件となる。
- 既存規定と重なる場合は両方を満たす。記事数・総容量を一律の製品ハード制限に変更するものではないが、1要求の走査量・保持量は有界とし、継続・再取得・部分結果の仕組みを定義する。

| 入力・処理 | 全文取得前／列挙時に必要な上限 | 解析・保持に必要な上限 | 超過・検査不能時 | 新規数値の状態 |
| --- | --- | --- | --- | --- |
| cms.config.json | 1ファイルのバイト数 | 深度、ノード・キー・配列要素数、単一値長、解析時間・結果保持量 | 第4.2節の全体不正と同じ限定停止。既存記事編集を維持 | TG09で確定・承認必須 |
| Git index | 1ファイルのバイト数 | エントリー数、パス長、拡張領域量、解析時間・保持量 | Git書込停止。ステージなしと表示しない | TG09で確定・承認必須 |
| Git config・packed-refs・loose ref・HEAD等の非objectメタデータ | 形式別の1ファイルバイト数、1要求の累積取得量 | 行・項目・ref数、単一値・パス長、解析時間・保持量 | 該当Git読取を未完了として表示、Git書込停止。記事編集は独立判定 | TG09で確定・承認必須 |
| 記事領域・Git ref等の列挙と索引 | 1要求の調査件数・時間。再帰操作は第34.4節も適用 | 未処理キュー、取得済み集合、索引・結果の保持量。既存キャッシュ予算も適用 | 部分結果・未調査・検査不能を区別。完全性が必要な保存・削除・Git操作は停止 | TG09で確定・承認必須 |
| 削除前退避マニフェスト | 1ファイルのバイト数 | エントリー数、深度、単一路径長、ノード数、解析時間・保持量 | 退避検証済みとせず削除禁止。元・退避物を変更しない | TG09で確定・承認必須 |
| 診断ログの再読込 | 1ファイルのバイト数、1要求の累積取得量 | レコード数、深度、単一値長、解析時間・保持量 | 該当ログの読取停止。記事編集・原文退避を維持 | TG09で確定・承認必須 |
| 復旧ドラフト・制御記録 | 原文は記事編集上限、世代数・全体容量は第33.3節。付随メタデータ・制御記録のバイト数も制限 | メタデータの深度・件数・値長、検証時間・結果保持量 | 該当候補を未検証／破損として隔離し、有界な救出を案内。ディスクへ適用しない | 原文・容量は既定値を維持。付随形式の数値はTG09・TG10で確定 |

- サイズ情報が取れない・途中で変わる場合も、有界チャンクで累積取得量を数える。全量を取得・展開・JSON化・配列化してから上限を確認する方式を禁止する。
- 件数・深度・ノード数・待機キュー等は構築中に適用する。時間上限だけでメモリ増幅の防止とみなさない。キャンセルと主UI応答を維持する。
- ref・index・設定等の予算超過は、異常な内容を安全と判定する根拠にならない。不完全な索引を全件検索・slug一意性・ステージなしの証拠へ使わない。
- マニフェストは、最大対応の退避対象からCMS自身が生成するものを再読込できるよう上限を整合させる。CMSが生成する設定・ドラフト等も対応する読込予算を満たす。安全な整合が成立しなければ方式・対応範囲を再合意する。
- 技術記録には、入力種別、入口API、読込前検査、構築中カウンター、停止時点、残存状態、UI影響範囲、回復操作、試験IDを対応付ける。未対応の入口・未確定セルを残して受け入れ完了としない。
