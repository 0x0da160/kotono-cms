# 決定

[ADR-0012](0012-passkey-only-login-whole-app-encryption.md) の設計（パスキーと回復コードで開く 1 つの鍵で、アプリ全体を暗号化する）は変えない。次の 2 点を改める。以下では、起動時に開くその鍵（ADR-0012 の「ログインの鍵」）を、第2章の表現に合わせて「ロック解除の鍵」と書く。

## 1. 以前の版との互換をなくす

1. **読むのは、いまの形式だけにする。** 以前の版のための経路と、移行のための処理をすべて削除した。
2. **削除したもの**
   - パスフレーズでの登録・認証・設定（ADR-0011 の 1.3）と、ロック解除の記録からパスフレーズの枠を外す処理（ADR-0012 の 1.1）。
   - 作業場所ごとの回復コード・パスフレーズ・パスキーの枠と、作業場所ごとに鍵を開く画面（ADR-0012 の 2.3）。
   - 移行の処理：ロック解除の記録に覚えていた作業場所の鍵を meta へ移す処理、以前の枠で開いた作業場所に枠を足す処理、暗号化した表示名を平文へ移す処理、平文の復旧ドラフトの包み直し（ADR-0011 の 2.3）。
   - 暗号化しない作業場所。
   - 書き出し（.kotono）の以前の形式（データ鍵を直接包んだ枠を持つもの。ADR-0012 の 3.1・3.4）。
3. **いまの形式**
   - ロック解除の記録（IndexedDB の `login`）：`{ v: 1, keyring, createdAt }`。ロック解除の鍵を、回復コードの枠（必須）とパスキーの枠で包んだもの。
   - 作業場所の meta：鍵の情報（`keyring`）は必須で、ロック解除の鍵で包んだ枠（種類 `login`）を持つ。
   - 書き出しのヘッダー：`{ v: 1, login: { slots, wrapped } }`。`slots` は書き出した端末の回復コード・パスキーの枠、`wrapped` はロック解除の鍵で包んだデータ鍵。先頭の `KOTONO-EXPORT/1` と、本文の追加認証データ（ヘッダー全体）は変えない。
4. **以前の版のデータの扱い**
   - パスフレーズの枠を持つ記録は読まず、パスキーの登録からやり直す。
   - ロック解除の鍵で包んだ枠のない作業場所（作業場所ごとの鍵だけのもの・暗号化していないもの）は「不完全」と示し、削除だけできる。
   - 以前の形式の書き出し（ADR-0012 の版 2 を含む）は読まない。
   - 包んでいない復旧ドラフトは読まない。

## 2. 表現は「ロック」と「ロック解除」の対にする

1. **起動時の認証を「ログイン」と呼ばない。** サーバーに身元を示して入る操作ではなく、端末内の鍵を開く操作なので、「ロック解除」と呼ぶ。閉じる操作は「ロック」。[ADR-0013](0013-header-menu-consolidation.md) で未決だった「ロック」の名前は、メニューの「ロック」のまま、対になる操作を「ロック解除」と呼ぶことで決まった。
2. **言葉の対応**

   | これまで | これから |
   |---|---|
   | ログイン（操作・画面・見出し） | ロック解除 |
   | ログインする | ロックを解除する |
   | ログインの画面 | ロック解除の画面 |
   | ログインの鍵・ログイン鍵 | ロック解除の鍵 |
   | ログインの記録 | ロック解除の記録 |
   | ログインの枠（作業場所の meta） | ロック解除の鍵で包んだ枠 |
   | ログインを作り直す | ロック解除の鍵を作り直す |
   | 解錠・解錠中 | ロック解除・ロック解除中 |
   | ロック・自動ロック | そのまま |

3. **画面の文言**
   - 起動時の画面：見出し「ロック解除」、ボタン「パスキーでロック解除」、回復コードの欄のボタン「ロック解除」。
   - メニュー：「ロック」。「設定」の見出し：「ロック解除」（パスキーの登録）と「自動ロック」。
   - 作業場所の一覧の印：「ロック解除中」。開けない作業場所は「開けません」。
   - 暗号化した書き出しを取り込むときのボタンは「開く」「パスキーで開く」にする。アプリのロックを解除するのではなく、書き出しを開く操作のため。
   - 作り直しは「ロック解除の鍵を作り直す…」。
4. **コード上の名前と保存する形式は変えない。** `LoginController`・`LOGIN_ID`・`login.svelte.ts`・`data-testid="login-…"`、鍵の枠の種類 `login`、IndexedDB のキー `login`、追加認証データ `kotono-cms/login/place` はそのまま。パスキーと回復コードの保存名 `kotono-login`（パスキー管理アプリ・パスワード管理に出る名前）も変えない。変えると、保存済みの回復コードとユーザー名が合わなくなる。
5. **これまでの文書は書き換えない。** ADR-0011〜0013 と仕様 3.2 の「ログイン」「解錠」は、当時の記録として残す。読み替えは上の表による。

# 理由

- 依頼により、以前の版との互換は要らない。移行の経路をなくすと、鍵の扱い（誤りの許されない所）の分岐が減り、試験する組み合わせも減る。
- 「ログイン」は、サーバーに身元を示して入る操作を思わせる。ここで行うのは端末内の鍵を開くことで、認証はどこにも送らない。メニューの「ロック」と対になる言葉にすれば、閉じる・開けるの関係がそのまま伝わる。
- 「解錠」と「ロック解除」が混ざると、同じ操作に 2 つの名前がつく。「ロック解除」にそろえる。

# 影響と注意

- **以前の版で作ったデータのうち、上の「以前の版のデータの扱い」に当たるものは開けない。** 中身は自動では消さない。
- **ADR-0012 の版でパスキーを登録して作った記録・作業場所・復旧ドラフトは、形式を変えていないので読める見込み**（コードの上での確認。実機では未確認）。その版で書き出した .kotono は読めないので、必要なら書き出し直す。
- パスキー管理アプリ・パスワード管理に出る名前は `kotono-login` のまま（上の 2.4）。
- 単体テストと E2E の名前・確認する文言を、新しい表現に合わせた。起動時の画面に「ログイン」が出ないことを E2E で確かめる。

# 未決・残る課題

- 仕様 3.2 の第39章（暗号化と解錠）への反映は別に行う（ADR-0012 と同じ）。
- パスキー管理アプリに出る名前 `kotono-login` を変えるか。変えるなら、保存済みの回復コードの扱いを決めてから行う。
